## Goal
Run the M1–M2 stores (instruments, symbol mappings, lineage, evaluation records) on PostgreSQL through one store code base, with their existing tests passing on PostgreSQL.

## Contracts
```python
class Database(Protocol):
    backend: Literal["sqlite", "postgresql"]
    def execute(self, sql: str, params: Mapping[str, object] = ...) -> None
    def fetchone(self, sql: str, params: Mapping[str, object] = ...) -> tuple | None
    def fetchall(self, sql: str, params: Mapping[str, object] = ...) -> list[tuple]
    def transaction(self) -> ContextManager[None]   # joins an open one; the outermost commits or rolls back all
    in_transaction: bool

class SqliteDatabase: ...       # wraps sqlite3.Connection (BEGIN IMMEDIATE)
class PostgresDatabase: ...     # wraps psycopg.Connection (READ COMMITTED; row locks where a rule needs them)

# Store constructors take a Database:
SqliteInstrumentRepository(db)   # name kept; works on either backend
SqliteSymbolResolver(db)
LineageStore(db)
EvaluationRunStore(db, *, calendars)
```

## Rules
1. **One store, two backends.** SQL uses named `:name` parameters. `PostgresDatabase` translates them to `%(name)s` with a strict pattern that ignores `::` casts and string literals. Statements are constants in the code, never built from input. Behaviour is identical: the same records, ids, errors and refusals.
2. **Errors are the same type.** Append-only refusals raise `AppendOnlyViolation` on both backends. Conflicts keep `LineageConflict` and `EvaluationRunConflict`. Driver exceptions don't leak through store methods.
3. **R1 and B1 stay true on PostgreSQL.** The genuine `57d4316` evaluation record reads back under its original id on both backends. Every replacement route is refused.
4. **Constructor compatibility.** Passing a raw `sqlite3.Connection` still works through a deprecation shim that wraps it in `SqliteDatabase`. The M2 report script and old notebooks keep running. The shim is removed only by a later reviewed task.
5. Mapping overlap and instrument lifecycle rules run inside one transaction, with `FOR UPDATE` on PostgreSQL (M3-01 rule 4). A concurrency test proves two overlapping mapping inserts can't both succeed.

## Implementation choices
Resolved: a thin port rather than an ORM, which would add a dependency and hide SQL. Resolved: existing class names are kept to avoid churn; renaming is cosmetic and left out.

## Acceptance tests
- Every existing store test passes on both backends; the count per backend is reported.
- Parameter translation: names, repeated names, `::` casts, quoted `:text` and an unknown name (raises).
- Concurrent overlapping mappings on PostgreSQL: exactly one commits.
- Old-format and current-format evaluation records, and lineage records, round-trip identically on both backends.

## Out of scope
New M3 stores (M3-04 onwards), copying existing data (M3-03), the CLI switch (M3-03).
