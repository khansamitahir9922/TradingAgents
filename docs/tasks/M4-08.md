## Goal
On restart, the Execution Worker:
- resolves uncertain orders by `client_order_id`, without resending them;
- re-gates orders still NEW;
- carries every unfinished cancel request forward, including those already in CANCEL_PENDING.

Every process republishes its unpublished outbox rows. All of this is proved with real processes killed at chosen points (G4; Laws 11, 14; PRD UC-13; ADR-004 §5; ADR-005 §6).

## Allowed files
- `investment_engine/execution/recovery.py` (new)
- `investment_engine/execution/worker.py`, `investment_engine/core/engine.py`: call recovery on start
- `tests/engine/test_recovery.py`, `tests/engine/process_harness.py` (new, test-only): starts the real entry points as OS processes, with fault points installed by a test-only wrapper module
- `docs/tasks/M4-08.md`, `PROGRESS.md`

## Rules
1. **Worker start-up order:**
   1. publish pending outbox rows;
   2. resolve SUBMITTING orders;
   3. resolve UNKNOWN orders;
   4. continue unfinished cancel requests (M4-07 rule 3: CANCEL_PENDING orders are resent);
   5. the normal step, where orders still NEW go through the gate again (G4).
2. **SUBMITTING** means the order was saved, and the broker may or may not have received it. Recovery calls `lookup(client_order_id)`:
   - **a report:** apply legal edges to the reported state, then ingest that order's messages;
   - **no record:** SUBMITTING → UNKNOWN (D20), and **never resend** (Law 14);
   - **a lookup error:** leave it SUBMITTING, and retry next step.
3. **UNKNOWN** is looked up the same way, once per step. A report resolves it. No record leaves it UNKNOWN, with each lookup result recorded.
4. **The Core Engine** on start publishes pending outbox rows and resumes its consumers from `processed_events`. Conversion is a single transaction, so there is no half-done work.
5. **Fault points are test-only.** Production modules contain no fault hooks or environment-variable triggers. The harness patches named functions inside the child process to stop it at a point, then calls `Popen.kill()`.
6. **Connection loss versus server restart** (clarification). A **dropped connection** is simulated by the harness closing the child's connection from the client side, through a test-only wrapper. A **PostgreSQL server restart** isn't done: the server is the owner's shared installation, and stopping it isn't an incidental test action. That case is recorded as "not run", with that reason.

## Acceptance tests
These run as real OS processes on PostgreSQL, with the simulated broker unless stated:
- Killed after SUBMITTING is committed, before `submit`: on restart, no record, so UNKNOWN; `submit` is never called again.
- Killed after `submit` returns, before SUBMITTED is saved: on restart, the lookup finds it, it becomes SUBMITTED, and its messages are ingested; there is one broker order.
- Killed mid-ingest, before the commit: the fill is recorded once.
- **Cancel crash points (B2):**
  - killed after CANCEL_PENDING and SENDING are committed, before `broker.cancel`: on restart the cancel is sent, and the order reaches CANCELLED;
  - killed after the broker accepted the cancel, before SENT is recorded: on restart it is resent (idempotent), and the CANCELLED message closes the request;
  - both with **trading disabled**, which doesn't block either.
- Core killed after approval and before conversion: on restart, it converts once. Core killed after conversion and before publishing: on restart, `order.created` is published once. The worker's NEW scan submits once in either case.
- Dropped connection mid-step: both processes reconnect, and the state is consistent.
- A cancel timeout (test double) followed by a restart: resent, then closed.

## Out of scope
Reconciliation with a `BrokerSnapshot` (M5), the broker's cancel-all (runbook), stopping the database server.
