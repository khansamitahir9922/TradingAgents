## Contracts
```python
class AccountKind(StrEnum): RESEARCH = "RESEARCH"; PAPER = "PAPER"     # D15
class Role(StrEnum): ADMIN = "ADMIN"; TRADER = "TRADER"; VIEWER = "VIEWER"

@dataclass(frozen=True)
class Account:
    account_id: str; kind: AccountKind; currency: str     # "USD" in v1
    effective_at: datetime                # when it exists in its own timeline (replay time for RESEARCH)
    recorded_at: datetime                 # when the command actually ran (LiveClock)

@dataclass(frozen=True)
class AutonomySetting:
    account_id: str; level: int          # 0, 1 or 2; 3 and 4 are refused in v1
    effective_at: datetime; recorded_at: datetime
    sequence: int                         # strictly increasing per account; orders equal effective times
    set_by: str; reason: str
    setting_id: str = field(init=False)   # "aut-" + SHA-256 of canonical content (sequence included)

@dataclass(frozen=True)
class Operator:
    operator_id: str; role: Role; active: bool; changed_at: datetime

class AccountRegistry:
    def __init__(self, db: Database, audit: AuditStore, clock: Clock) -> None
    def create_account(self, account_id, kind, currency, *, by: Actor, reason: str,
                       effective_at: datetime | None = None) -> Account
    def set_autonomy(self, account_id, level, *, by: Actor, reason: str,
                     effective_at: datetime | None = None) -> AutonomySetting
    def autonomy_at(self, account_id, at: datetime) -> AutonomySetting        # greatest (effective_at, sequence) <= at
    def bootstrap_admin(self, operator_id, *, os_user: str) -> Operator       # only while no operator exists
    def add_operator(self, operator_id, role, *, by: Actor, reason: str) -> Operator
    def deactivate_operator(self, operator_id, *, by: Actor, reason: str) -> Operator
    def operator(self, operator_id, at: datetime) -> Operator
```

## Rules
1. **Default Level 0.** A new account starts at Level 0 (advisory). Levels 3 and 4 always raise "disabled in v1". A RESEARCH account may use Levels 0–2 for replay demonstrations; a PAPER account's level only matters once a strategy is promoted (M3-10, D15).
2. **Admin only.** Creating accounts, setting autonomy and managing operators require an active ADMIN operator (PRD §4). Every change is a new row (autonomy history and operator history are append-only) plus an AuditEvent in the same transaction.
3. **Bootstrap.** `bootstrap_admin` works once, only while no operator exists. It's audited with actor PROCESS `admin-cli` and the OS user. Afterwards it raises.
4. **No deletes.** Accounts and operators are never deleted and ids are never reused. An operator is deactivated, and an inactive operator can't act.
5. **Research setup in replay time; no backdating for paper** (Codex S2; re-review R2 and S2). For a RESEARCH account, `create_account` and `set_autonomy` take an explicit `effective_at`, a replay time, and record the live `recorded_at` beside it. Both appear in the audit event and every display. Settings take effect in replay only from their declared `effective_at`, never from "now". For a PAPER account, `effective_at` must be omitted: it's set to the LiveClock's `recorded_at`, and backdating raises. A RESEARCH `effective_at` can't move: a later setting needs a later or equal `effective_at` and a higher `sequence`.
   - **Authorization uses the real command time.** Every privileged command, for RESEARCH accounts too, checks the named operator's active role at the **current** time from the injected LiveClock, never at the replay time. A deactivated or wrong-role operator therefore can't act by choosing an earlier replay time. Today's operator can still configure and approve a 2021 replay. The operator registry itself is live-time only: operators have no `effective_at` and are never backdated.
   - **Identities exclude provenance** (re-review S2). `setting_id`, and every other hashed identity derived from setup (accounts, limit versions, starting states, then snapshots and lineage), hashes the deterministic content (`effective_at`, `sequence`, values and reason) but **not** `recorded_at`, the OS user or the command time. Those are provenance, stored beside the record and in its audit event. Two independent setups with the same replay inputs therefore produce identical ids, and nothing is lost.
6. **Serialization of control changes** (Codex S4). Every change to an account's controls (autonomy here; limits, rules and halts in M3-06) and every approval (M3-13) first takes the account's transaction-scoped advisory lock (`"account-control|<account_id>"`, M3-01's key function). The next `sequence` is read and written under it. `bootstrap_admin` takes a global `"operators-bootstrap"` lock and re-checks that no operator exists inside it, so two concurrent bootstraps produce exactly one admin.
7. **CLI.** `accounts create|set-autonomy|show|list` and `operators bootstrap-admin|add|deactivate|list`, each requiring `--operator ID` (except bootstrap) and `--reason` for changes. RESEARCH changes require `--effective-at T`; PAPER changes refuse it. Output is plain ASCII and states "Level N (Advisory | Approved paper | Automatic paper)" and the account kind.

## Acceptance tests
- Default level 0; levels 3, 4, -1 and 5 refused; history answers "what was the level at T" across changes.
- A Trader or Viewer can't change anything; an inactive Admin can't; each refusal changes nothing and writes no event.
- Every successful change writes exactly one AuditEvent with before and after, in the same transaction (rolled back together on a forced failure).
- Bootstrap works once; two concurrent bootstraps on PostgreSQL give exactly one admin; ids can't be reused.
- `autonomy_at` with equal `effective_at` values resolves by `sequence`; the history 1 -> 2 -> 1 gives three distinct `setting_id`s (used by M3-13's "changed since proposal" check).
- A RESEARCH setting at a 2019 replay time is effective in 2019 replay lookups and carries today's `recorded_at`; a PAPER backdate is refused; a RESEARCH `effective_at` earlier than the account's latest setting is refused.
- An operator bootstrapped today configures a RESEARCH account at a 2019 `effective_at` (authorized at today's time). An operator deactivated today is refused for any `effective_at`, earlier ones included. The audit event shows both times.
- Two setups made at different real times with identical replay inputs give identical **deterministic payloads and ids** (`setting_id`, account identity), while their provenance (`recorded_at`, OS user) differs and is kept. Both parts are asserted; full dataclass equality, which includes provenance, is not the identity requirement (Codex acceptance note 2).
- CLI happy paths and refusals, against PostgreSQL.
