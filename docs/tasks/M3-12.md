## Goal
Run G1 steps 6–9 for one account and one view: reference price, snapshot, sizing, policy, risk, any reduction, then approval routing by autonomy level. Every step that ran is recorded exactly; every step that didn't is recorded as not run. Every decision is reconstructable and replay-deterministic (Laws 5, 9, 12, 18; Part J replay test).

## Rules
1. **Order of work.**
   1. **Validate first** (Codex re-review R3). The account must exist and the time mode must match its kind: RESEARCH needs an explicit replay `at`; PAPER needs the LiveClock's time, and a supplied replay time raises. A missing account returns PREREQUISITE_MISSING **before any mutation**. That ProposalRecord is a returned diagnostic only and is **not persisted**: an unknown-account request writes and expires nothing (Codex acceptance note 3). An existing account missing other prerequisites gets the normal stored record.
   2. Expire **only this account's** due intents (`expire_due(account_id, at)`), on that account's own timeline.
   3. Gather the prerequisites at `at`:
   - the account and its autonomy setting (M3-05);
   - risk limits and policy rules (M3-06);
   - the view's LineageRecord (M2-07);
   - the instrument;
   - the RawReference (M3-07 rule 1);
   - the snapshot (M3-07).
2. **Outcome matrix** (Codex B3). Exactly these records exist for each outcome:

   | Outcome | Intent versions | PolicyDecision | RiskDecision | IntentLineage | Snapshot stored |
   |---|---|---|---|---|---|
   | PREREQUISITE_MISSING (names in `missing`) | none | none | none | none | only if it was built |
   | NO_INTENT | none | none | none | none | yes |
   | POLICY_REJECTED | v1 | v1: run, failed | v1: `NotRun("risk", "policy rejected: risk not evaluated")` | v1 | yes |
   | RISK_REJECTED | v1 (or v2 after a reduction) | each version: run | each version: run | each version | yes |
   | REDUCE then routed | v1 SUPERSEDED, v2 | v1 and v2: run | v1 REDUCE, v2 APPROVE | v1 and v2 | yes |
   | AWAITING_APPROVAL / APPROVED | final version | run, passed | run, APPROVE | each version | yes |
   | EXPIRED_ON_ARRIVAL | as above, then EXPIRED | run, passed | run, APPROVE | each version | yes |

   A not-run check is never stored, displayed or counted as a pass or a failure. No version, decision or result is invented. Pre-reduction decisions stay in history through v1's lineage record.
3. **Checks.** Create v1 PROPOSED, then policy; a failure is POLICY_REJECTED. Then risk: REJECT is RISK_REJECTED. REDUCE marks v1 SUPERSEDED and creates v2, which runs policy and risk again (M3-11 rule 3). A HaltRequest records the latched halt (M3-06).
4. **BUY admission is serialized per account and session** (Codex B5).
   - Before risk runs on a BUY, the transaction takes the advisory lock `"buy-admission|<account_id>|<target_session>"` (M3-01's key function), after the account-control lock (lock order: account-control, then buy-admission). Under it, it reads `IntentStore.admitted_buys(account, session, excluding=intent_id)` and `was_admitted(intent_id)`, and passes both to risk (re-review S3).
   - The qualifying transition (into AWAITING_APPROVAL or APPROVED) commits while the lock is held.
   - Concurrent proposals for different views of the same account and session are therefore admitted one at a time.
   - A reduced v2, or an intent already admitted, doesn't take a new slot. Idempotent re-runs, later expiry or decline, and rolled-back transactions don't change the count.
   - No service or broker is added: this is a database lock inside the existing transaction.
5. **Routing by autonomy, with legal G2 paths only** (S5).
   - **Level 1:** PROPOSED -> AWAITING_APPROVAL with `approval_deadline` = the open of `target_session` (D11). If `at >= approval_deadline` already, AWAITING_APPROVAL -> EXPIRED follows in the same transaction (outcome EXPIRED_ON_ARRIVAL).
   - **Level 2:** PROPOSED -> APPROVED with `approved_by` = PROCESS `core-engine` ("Level 2 rule"), `approved_at = at` and `approval_expires_at` = the close of `target_session`, but never later than the view's `valid_until` (D10, D11). If `at >= approval_expires_at`, APPROVED -> EXPIRED follows (EXPIRED_ON_ARRIVAL).
   - There's no PROPOSED -> EXPIRED edge and none is added. Both boundaries use `>=`.
6. **Atomic and audited.** Everything for one (account, view) commits in one managed transaction: snapshot, intent versions, transitions, decisions, halt, intent lineage, ProposalRecord and audit events. A failure at any write leaves nothing, and neither takes nor frees an admission slot.
7. **Idempotent.** Re-running `propose` for the same account and view returns the stored ProposalRecord and changes nothing. The intent id is deterministic (M3-08 rule 1).
8. **View lineage is unchanged.** M2's `LineageRecord.portfolio_snapshot` and `risk_versions` stay None, because they describe the view. The final version's IntentLineageRecord id is set as the intent's `lineage_id`.
9. **Replay knowledge** (S2). `propose_over_replay` runs views in time order against one RESEARCH account.
   - `at = view.generated_at + proposal_delay`. `view.generated_at` already includes the feed's latency; `proposal_delay` (default 0) is a separate, named processing delay.
   - Every snapshot, reference and ADV read goes through `knowledge`. Replay uses M2's ReplayKnowledgeReader fed by the same ReplayFeed, so delivery time and equal-time sequence are respected; plain availability reads are not used.
   - Account, autonomy, limits and starting state must be effective at or before each `at` in replay time (M3-05 rule 5, M3-06 rule 6), or the outcome is PREREQUISITE_MISSING.
   - M3 has no fills, so holdings stay at the declared start; every output says so.
   - Two runs into fresh databases give identical ProposalRecords, intents, decisions and lineage ids, **given the same replay setup inputs** (effective times, sequences, values). Identities hash that deterministic content, not command provenance (`recorded_at`, command time, OS user), which is stored beside it (M3-05 rule 5, re-review S2). Setups recreated on different days still match. PAPER accounts can't be replayed.
10. **Timelines never mix** (R3). Each RESEARCH account's expiry runs only on its own replay time; PAPER expiry runs only on live time (`expire_paper_due`). No call applies one account's clock to another account, or a replay time to PAPER state. The legal G2 edges, compare-and-set and atomic audit are unchanged.
11. **No orders, no outbox** (M3 README). Nothing here touches broker code or credentials.

## Acceptance tests
- **The outcome matrix, table-driven, end to end on PostgreSQL.** One row each: missing account, autonomy, limits, rules, reference or snapshot (PREREQUISITE_MISSING); NO_INTENT (ABSTAIN, NEUTRAL); POLICY_REJECTED (Level 0; PAPER promotion); RISK_REJECTED; REDUCE then AWAITING_APPROVAL; Level 2 APPROVED; EXPIRED_ON_ARRIVAL at Levels 1 and 2. Each asserts exactly the records above exist and nothing else, with `NotRun` where shown. The exception is an unknown account: its PREREQUISITE_MISSING record is returned but not stored, and the database is unchanged.
- **First BUY from the default cash-only account** reaches AWAITING_APPROVAL with the decision bar's raw close as reference (B1).
- **Atomicity:** a failure injected at each write in turn leaves no intent, snapshot, lineage, record, audit event or admission count change.
- **Admission race (B5).** Two connections with a barrier, four of five slots taken, two different views: exactly one new intent is admitted and the other is RISK_REJECTED by `daily_buys`, repeated 50 times. Also: a reduced v2 takes no extra slot; AWAITING_APPROVAL -> APPROVED takes none; idempotent reruns, expiry, decline and a rolled-back proposal leave the count unchanged.
- **Boundaries:** a proposal at exactly the deadline (`>=`) is EXPIRED_ON_ARRIVAL through legal edges.
- **Replay:**
  - a correction available before but delivered after T doesn't affect the reference, snapshot or ADV at T;
  - equal-time sequence ordering;
  - a missing expected session gives PREREQUISITE_MISSING, never an older bar;
  - settings effective after `at` aren't used;
  - determinism across two fresh databases.
- **Expiry:** AWAITING_APPROVAL past the open and APPROVED past the close move to EXPIRED, with audit events.
- **Two research timelines (R3):** accounts A (replay 2021, intent awaiting before its deadline) and B (replay 2024) in one PostgreSQL database. Proposing and expiring B leaves A's state and audit history unchanged. Expiring A at its own boundary changes only A. A proposal for a missing account expires nothing. A supplied replay time for a PAPER account is refused, also through expiry.
- Two replay setups created at different real times with the same inputs give identical ids (S2).
- No import of broker, kill-switch or outbox code (an import scan in `test_intent_pipeline.py`).
