## Goal
Store orders, their transitions, fills, broker anomalies, cancel requests and gate decisions on PostgreSQL. All of it goes through one shared state-machine module used by both writers. Every edge of the frozen G3 lifecycle has exactly one owning process, and every write is a compare-and-set on `aggregate_version`. This task also defines the event envelope and the outbox-writer port, so later tasks can publish without depending forward (Laws 10, 11, 14; G3; ADR-004 §1, §3; ADR-005; Part H).

## Contracts
```python
class OrderState(StrEnum):  # G3, exactly as frozen (D19, D20)
    NEW, GATE_REJECTED, SUBMITTING, SUBMITTED, PARTIALLY_FILLED, FILLED, CANCEL_PENDING, CANCELLED, REJECTED, EXPIRED, UNKNOWN
class ProcessRole(StrEnum):
    CORE = "core-engine"; EXECUTION = "execution-worker"

EDGES: Mapping[OrderState, frozenset[OrderState]]   # G3; UNKNOWN resolves to SUBMITTED, PARTIALLY_FILLED, FILLED,
                                                    # CANCELLED, REJECTED or EXPIRED; never to SUBMITTING
OWNER: Mapping[tuple[OrderState | None, OrderState], ProcessRole]  # (None, NEW) -> CORE; all others -> EXECUTION
ACCOUNTING_STATES = frozenset({PARTIALLY_FILLED, CANCEL_PENDING, CANCELLED, EXPIRED})  # rule 4

@dataclass(frozen=True)
class Order:  # immutable after creation
    order_id: str; client_order_id: str; intent_id: str; intent_version: int; intent_content_id: str
    position_fingerprint: str        # the proposal's economic fingerprint (M4-05 rule 3), pinned at conversion
    account_id: str; account_kind: AccountKind; instrument_id: str; side: Side; quantity: Decimal
    order_type: str; limit_price: Decimal; time_in_force: str; target_session: date; created_at: datetime
@dataclass(frozen=True)
class OrderStatus:
    order_id: str; state: OrderState; aggregate_version: int; filled_qty: Decimal; avg_price: Decimal | None
    broker_order_id: str | None; anomalies: int
@dataclass(frozen=True)
class Fill:  # Part H plus provenance (M4-06 rule 4)
    fill_id: str; order_id: str; quantity: Decimal; price: Decimal; fee: Decimal; currency: str
    executed_at: datetime; delivered_at: datetime; recorded_at: datetime; broker_fill_id: str; provenance: str
@dataclass(frozen=True)
class CancelRequest:  # a command aggregate of its own (rule 6), not an order state change
    cancel_id: str; order_id: str; requested_by: Actor; requested_at: datetime; reason: str
class CancelProgress(StrEnum):
    REQUESTED, SENDING, SENT, CLOSED      # CLOSED carries the outcome: CANCELLED, TOO_LATE, NOTHING_TO_CANCEL
@dataclass(frozen=True)
class GateDecision:
    order_id: str; attempt: int; passed: bool; checks: tuple[CheckResult, ...]; checked_at: datetime; inputs: str

class OutboxWriter(Protocol):          # implemented by M4-01's Outbox; a recording double in tests
    def add(self, envelope: EventEnvelope) -> None
class OrderStore:
    def __init__(self, db, *, role: ProcessRole, audit: AuditStore, outbox: OutboxWriter): ...
    def create(self, order: Order, *, by: Actor, correlation_id: str) -> OrderStatus                       # CORE
    def transition(self, order_id: str, to: OrderState, *, expected_aggregate_version: int, at: datetime,
                   reason: str, broker_ref: str | None = None, gate: GateDecision | None = None) -> OrderStatus
    def record_fill(self, fill: Fill, *, expected_aggregate_version: int) -> FillOutcome                  # EXECUTION
    def record_anomaly(self, order_id: str, *, kind: str, detail: str, at: datetime, broker_ref: str) -> None
    def request_cancel(self, request: CancelRequest, *, correlation_id: str) -> CancelRequest              # CORE
    def cancel_progress(self, cancel_id: str, to: CancelProgress, *, expected_version: int, at: datetime,
                        outcome: str | None = None) -> int                                                  # EXECUTION
    def get(self, order_id) -> tuple[Order, OrderStatus]; def by_client_id(self, client_order_id) -> ...
    def in_states(self, *states) -> list[tuple[Order, OrderStatus]]; def history(self, order_id) -> list[OrderTransition]
    def fills(self, order_id) -> list[Fill]; def open_cancels(self) -> list[tuple[CancelRequest, CancelProgress, int]]
    def as_of(self, account_id: str, at: datetime) -> list[tuple[Order, OrderState, Decimal]]   # point in time (M4-09)
class FillOutcome(StrEnum): RECORDED, DUPLICATE, CONFLICT, REFUSED   # CONFLICT/REFUSED are stored as anomalies
```

## Rules
1. **The edges are exactly G3** (ADR-004 §1). There is no PARTIALLY_FILLED → EXPIRED (D19), and nothing leaves UNKNOWN without a broker report (D20). GATE_REJECTED, REJECTED, FILLED, CANCELLED and EXPIRED are final **states**. One message may need several legal edges in a row, such as SUBMITTING → SUBMITTED → PARTIALLY_FILLED. Each edge is then its own compare-and-set, its own version and its own event, all in one transaction.
2. **Ownership.** The store's `role` is fixed when it is built. CORE creates NEW and records cancel requests; EXECUTION does everything else. A wrong-role call raises `WrongProcess` and writes nothing. Each connection also sets `investment_engine.process_role` with `SET LOCAL` inside every write transaction, so the setting can't leak between pooled uses. A trigger refuses a transition, fill, anomaly, gate or cancel-progress row whose owner differs. An **unset or unknown role fails closed**. This is a consistency check, **not authentication**: any client can set the variable. Enforcement is still by convention until M7's OS users (ADR-002 §5). Tests cover both the store path and raw SQL.
3. **Compare-and-set** (Law 10). Every write to an order (a state edge or a fill-accounting update) is `UPDATE ... SET aggregate_version = v + 1 ... WHERE order_id = ? AND aggregate_version = v`. Zero rows raises `StaleWrite`. The trigger refuses:
   - any change to an immutable `Order` field;
   - a version step other than +1;
   - a state change not in `EDGES`;
   - a quantity change outside rule 4.
4. **Fill accounting is not a state edge** (the B1 matrix). A new `broker_fill_id` updates `filled_qty` and `avg_price` with a compare-and-set (+1 version, one `order.fill_recorded` event). The state changes only along an existing G3 edge:

   | Order state when the fill arrives | Effect |
   |---|---|
   | SUBMITTED, CANCEL_PENDING | → PARTIALLY_FILLED, or FILLED if complete (G3 edges; late fills accepted) |
   | PARTIALLY_FILLED | accounting update; → FILLED if complete; otherwise the state is unchanged (no self-edge) |
   | SUBMITTING (fill before the ack) | → SUBMITTED, then as SUBMITTED (two edges) |
   | UNKNOWN | the resolution edge to PARTIALLY_FILLED or FILLED |
   | CANCELLED, EXPIRED (a delayed fill executed before the cancel or expiry) | **accounting only; the state stays final.** A fill that would complete the order is recorded with a `fill_after_final` anomaly for M5 to reconcile. |
   | NEW, GATE_REJECTED, REJECTED, FILLED | **refused**: stored as an anomaly, never as a fill (Part J: a rejected order never becomes FILLED) |

   The same `broker_fill_id` with identical content is `DUPLICATE` and changes nothing. With **different** content it is `CONFLICT`: refused and stored as an anomaly. An overfill is `REFUSED`. `avg_price` is a volume-weighted Decimal average, computed in an explicit local decimal context.
5. **Ids** are derived deterministically from the intent id and version (`order_id`, `client_order_id`), and one intent version gives at most one order. Fill and anomaly ids are derived from the broker's ids.
6. **Cancel requests are their own aggregate** (`aggregate_type = "cancel_request"`). Version 1 is REQUESTED (CORE); later progress rows are EXECUTION's, each a compare-and-set +1. CLOSED is final and carries the outcome. The request's progress never changes the order's version.
7. **Events, exactly one per version** (B3; exhaustive):

   | Aggregate | Write (one compare-and-set, +1 version) | Its one event |
   |---|---|---|
   | order | create (v1) | `order.created` |
   | order | a state edge **without** a fill (incl. NEW → SUBMITTING or GATE_REJECTED with its gate decision) | `order.state_changed` |
   | order | a fill, **whether or not it also changes the state** | `order.fill_recorded`, carrying the resulting state |
   | cancel_request | REQUESTED (v1) | `cancel.requested` |
   | cancel_request | SENDING, SENT, CLOSED | `cancel.progressed` |

   A fill and the state change it causes are **one** write and **one** event. For example, SUBMITTED v2 plus a partial fill gives PARTIALLY_FILLED v3, with one v3 `order.fill_recorded`. A message needing a state edge **and** a fill writes them in sequence. For example, a fill delivered before the ack gives SUBMITTING v2 → SUBMITTED v3 (`order.state_changed`), then → PARTIALLY_FILLED or FILLED v4 (`order.fill_recorded`). Each event's `aggregate_version` is the version its write created, so there are no gaps and no reuse.

   **Gate decisions** are part of their edge's write. **Anomalies** create no version and **publish no event**. They are append-only rows that reference the order version current when recorded, with their audit event.
8. **Append-only** (Law 8). `order_transitions`, `fills`, `broker_anomalies`, `cancel_requests`, `cancel_progress` and `gate_decisions` refuse UPDATE, DELETE and TRUNCATE. Only the `orders` status columns change, and only under rules 3 and 4.
9. **Audit and outbox in the same transaction.** Every write adds its audit event (actor = the process). Every **versioned** write (rule 7) also adds its one outbox envelope through the injected `OutboxWriter`; anomalies add audit only. `add` outside a transaction raises.
10. **Point in time** (M4-09). `as_of(account, at)` gives each order's state and filled quantity as known at `at`. It uses only transitions and fills whose **recorded time is ≤ `at`**, never today's status. A write recorded after `at` is invisible at `at`.

## Acceptance tests
- Every pair of states: the legal edges match G3 exactly; everything else raises `IllegalTransition` and writes nothing.
- Ownership: every edge with the right role and the wrong one; raw-SQL rows with an unset, unknown or wrong role are refused by the trigger; a `SET LOCAL` doesn't leak to the next transaction on the same connection.
- Compare-and-set races on PostgreSQL, 20 repetitions: exactly one writer wins.
- The fill matrix of rule 4, row by row: two partial fills, then a third that completes; a CANCELLED ack ingested before an earlier delayed fill (accounting only, the state stays CANCELLED); a delayed fill completing a CANCELLED order (anomaly); a fill on REJECTED (refused, anomaly; never FILLED); a fill before the ack; identical and conflicting duplicates; an overfill.
- Event numbering: SUBMITTED v2 plus a partial fill gives one v3 `order.fill_recorded`; a fill before the ack gives v3 `order.state_changed` and v4 `order.fill_recorded`; a gate decision with its edge gives one event; cancel progress versions separately; an anomaly adds no version or event. All are contiguous.
- The trigger refuses an immutable-field update, a version jump, an illegal edge, and UPDATE or DELETE on the append-only tables.
- `as_of` returns the historical state, not the current one, after later transitions. A write recorded exactly at `at` is visible at `at`; one recorded a microsecond after isn't.
- Typed audit payloads decode in a fresh process (registry).
