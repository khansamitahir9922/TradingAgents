## Rules
1. **Fail closed.** No effective limits means `NoLimits`, which the pipeline records as PREREQUISITE_MISSING with no intent (M3-12 rule 2). The shipped `proposed_limits.json` is applied only when an Admin runs `limits publish --file` explicitly; its header says the values are owner decisions D1–D9 and D13. The file has a `risk` and a `policy` section. `limits publish --file` publishes both as two new versions in one transaction (one audit event each).
2. **Versions never change.** Publishing creates the next version, effective from its publish time (PAPER) or its declared `effective_at` (RESEARCH, rule 6); old versions stay readable. A restricted-list change (`restricted add|remove ID --reason`) publishes a new PolicyRules version. Each publish is audited in the same transaction.
3. **Validation.** Fractions are Decimal in (0, 1] (gross exposure up to exactly 1); integers are positive; `long_only=False` is refused in v1; unknown keys in a file are refused; floats in the JSON are refused (strings or integers only), so no binary rounding enters money rules.
4. **Halts are latched, and clearing resets the baseline** (D3, Codex S6). A halt stays until an Admin clears it, even if the account recovers. Clearing records the current equity as the new drawdown baseline: afterwards the drawdown is measured from the highest equity since the clear (M3-07 rule 5), so clearing doesn't immediately re-trigger. If the owner prefers the halt to stay measured from the old peak, D3's alternative applies, and an Admin must then also raise the limit or the halt will re-trigger at once; the clear command says so. Halt history is append-only and audited.
5. Admin role required for publish, restricted changes and clearing a halt (M3-05 rule 2).
6. **Versions in replay time; no backdating for paper** (Codex S2). Publishing for a RESEARCH account takes an explicit `effective_at` replay time (`--effective-at`), with the live `recorded_at` stored beside it. Lookups at T use `effective_at`, so a 2019 replay never sees a set of limits that the account didn't declare for 2019. For a PAPER account, `effective_at` is the publish time and can't be supplied. Authorization uses the real command time, and version identities exclude provenance (M3-05 rule 5, re-review R2/S2).
7. **Serialized publication** (Codex S4). Publish, restricted changes, set-halt and clear-halt take the account-control lock (M3-05 rule 6). Version numbers are assigned under it: consecutive, with no gaps and no duplicates under concurrency.

## Acceptance tests
- No limits: lookups raise `NoLimits`. Publishing the proposed file gives version 1 with exactly the D-values.
- Versions answer "what was effective at T" across several publishes; old versions unchanged; UPDATE and DELETE refused.
- Each validation refusal (float, out-of-range fraction, unknown key, `long_only=false`) publishes nothing and writes no event.
- Restricted add and remove create new policy versions with audit events.
- A halt persists after recovery until cleared by an Admin; a Trader can't clear it; after clearing, the baseline is the clearing equity, and a further 15% fall re-halts.
- Restricted lists given in different orders, or with duplicates, produce identical PolicyRules, audit bytes and ids; empty and non-empty lists round-trip through the store and the audit store, also in a fresh process.
- Concurrent publishes on PostgreSQL produce consecutive versions with no gaps or duplicates.
- RESEARCH limits published today with `--effective-at 2019-01-02` are found by a 2019 lookup and not by a 2018 one; PAPER refuses `--effective-at`.
