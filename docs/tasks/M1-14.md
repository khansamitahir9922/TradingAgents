## Goal
Replay stored market data through a `ReplayClock`, **deterministically**. A replay **never delivers a revision before it was available**: not as its own event, and not hidden inside an earlier event. Every event's timestamps follow Law 5 exactly, and they're computed during replay, **never written back** to storage.

## The three timestamps of a replay event
Each event delivers **exactly one stored revision** (its payload). The replay event's own timestamps are:

| Timestamp | Definition |
|---|---|
| `event_time` | When the information became available in the replayed world: **the payload revision's `available_from`** |
| `received_at` | `event_time + latency` (Law 5, with a configured simulated latency, default 0) |
| `processed_at` | The `ReplayClock` time when the event is handed to the consumer, which is equal to `received_at` (replay simulates no processing delay) |

**Why this resolves the Law 5 conflict.** In v0.1, a bar's delivery time was `max(end_time, first available_from) + latency`, which isn't Law 5's `event_time + latency` when a bar is first observed late. Now the replay event's `event_time` **is** the availability time, so `received_at = event_time + latency` holds for every event:
- For backfill (`available_from = end_time`), `event_time` equals the bar's end, which is Law 5's usual case.
- For a bar first observed late, the event happens when it became known, never earlier.

The payload keeps its own stored times (`end_time`, `event_time`, `received_at`, `available_from`) for display and lineage. They're never overwritten.

## Contracts
```python
@dataclass(frozen=True)
class ReplayEvent:
    kind: Literal["CORPORATE_ACTION", "CANDLE_REVISED", "BAR_CLOSED"]
    source: str                 # provider of the payload
    event_time: datetime        # == payload.available_from
    received_at: datetime       # == event_time + latency
    processed_at: datetime      # == received_at
    sequence: int               # strictly increasing across the whole replay
    payload: Candle | CorporateAction   # exactly one stored revision, unmodified

class ReplayFeed:
    def __init__(self, reader: MarketDataReader, clock: ReplayClock, *,
                 sources: Sequence[str], instrument_ids: Sequence[str], timeframes: Sequence[Timeframe],
                 start: datetime, end: datetime, latency: timedelta = timedelta(0))
    def __iter__(self) -> Iterator[ReplayEvent]
```

## Delivery rules
1. **Candidates** are fetched **per provider** with `candle_revisions_available_between(source, …, start - latency, end - latency)` and `action_revisions_available_between(...)`. Each stored revision gives exactly one event:
   - candle **revision 1** → `BAR_CLOSED`;
   - candle **revision ≥ 2** → `CANDLE_REVISED`;
   - corporate action (any revision) → `CORPORATE_ACTION`.
2. **No early corrections.** A `BAR_CLOSED` event **always carries revision 1**. It never carries "the latest revision available at delivery". Each later revision arrives only in its own `CANDLE_REVISED` event, at its own `available_from + latency`. Latency shifts every event equally, so it can never pull a correction forward. (In v0.1, a 5-second latency could have let a revision available 3 seconds after the bar ride inside `BAR_CLOSED`.)
3. **Window boundaries.** An event is delivered **iff `start <= received_at < end`** (half-open, by delivery time). The consequences:
   - a bar whose end is inside the window but whose `received_at` falls at or after `end` is **not** delivered in this window;
   - a correction to an old bar is delivered if it **arrives** inside the window, even when the bar itself ended before `start`;
   - events that arrived before `start` aren't replayed. Consumers that need earlier state start the replay earlier (warm-up). A snapshot loader is out of scope.
4. **Delayed delivery.** `latency >= 0` (a negative value raises) shifts every event's `received_at` equally. The clock is advanced to each event's `received_at` before it's yielded, and it never moves backwards.
5. **Only CLOSED bars** are delivered (Law 7). A FORMING payload from any source raises an error and is never passed on.
6. **Ordering.** Events are sorted by a key that contains the payload's **full identity plus revision**, so no two distinct events can tie:
   - `CORPORATE_ACTION`: `(received_at, 0, source, instrument_id, ex_date, action_type_rank, revision)`;
   - `CANDLE_REVISED`: `(received_at, 1, source, instrument_id, timeframe_rank, start_time, revision)`;
   - `BAR_CLOSED`: `(received_at, 2, source, instrument_id, timeframe_rank, start_time, revision)`.

   The second element is `kind_rank`. `action_type_rank` follows `ActionType`'s declaration order (`SPLIT` 0, `DIVIDEND` 1, `SYMBOL_CHANGE` 2, `DELISTING` 3), the same as in M1-11. `timeframe_rank` follows `Timeframe` (`D1` 0, `H1` 1). `sequence` is assigned in this order (Law 5's tie-break). **The result never depends on the order in which the reader returns rows.**
7. **Replay never writes.** The store is unchanged after any replay.

## Implementation choices
**Resolved**
- **One event per stored revision**, selected by **revision identity, not by delivery time**. This is what makes early leakage impossible.
- **No outbox, no persisted events** (ADR-005: event contracts only before M4).
- **Equal-time order puts corporate actions first**, so a split known at the start of its ex-date is delivered before that day's bars.
- **Providers stay separate.** Every event names its provider, and replay never merges or reconciles providers.

**Unresolved:** none.

## Acceptance tests
**Friday correction** (the M1-11 fixture, latency 0):

| Replay window | Delivered |
|---|---|
| Monday → Thursday | Monday's `BAR_CLOSED` (revision 1); no `CANDLE_REVISED` |
| Monday → Saturday | that, plus `CANDLE_REVISED` (revision 2) at Friday 21:00 UTC |
| Saturday → next week | nothing for Monday's bar: both events arrived before the window |
| Thursday → Saturday | only the `CANDLE_REVISED` (the correction arrives in the window although the bar ended before it) |

**Latency can't leak a correction (Codex finding 3):**
- revision 1 is available at the bar end E, and revision 2 at E + 3 s, with `latency = 5 s`;
- expect `BAR_CLOSED` at E + 5 s **carrying revision 1**, then `CANDLE_REVISED` at E + 8 s carrying revision 2.

**Late first observation.** A bar ending at E whose revision 1 is `OBSERVED` at E + 2 h:
- `event_time = E + 2 h`, `received_at = E + 2 h + latency`;
- `payload.end_time = E` is preserved.

**Window edge.** A bar ending at `end - 1 s` with `latency = 5 s` isn't delivered. With `latency = 0`, it is.

**Corporate actions:**
- a backfilled split is delivered at the start of its ex-date, before that day's `BAR_CLOSED`;
- a later dividend correction is delivered only at its own `available_from + latency`;
- a replay ending before the correction never sees it.

**Two providers:**
- `yfinance` and `testvendor` bars for the same time are separate events with their own `source`, ordered by rule 6;
- a `testvendor` correction never appears as a `yfinance` event.

**Shuffled input (Codex finding):**
- A split and a dividend share provider, instrument, `available_from`, ex-date and revision 1.
- A reader stub returns them, together with the other fixture events, in their original order, in reverse, and in 20 seeded random permutations.
- Every run yields **identical** events and sequence numbers, with the split before the dividend.

**Other cases:**
- **Determinism:** two replays give identical events, sequences included. Equal-time events follow rule 6.
- **Clock:** it equals each event's `received_at` at the moment of yield, and never moves backwards. A negative latency raises.
- **FORMING:** a reader stub returning a FORMING bar causes an error.
- **Store unchanged:** file hashes are identical before and after a replay.
- **Labels:** payloads keep `availability_basis`, so `BACKFILL_ASSUMED` stays visible downstream.
