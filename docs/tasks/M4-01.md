## Goal
Implement save-then-publish across processes, through the database only. A state change and its outbox row commit together. A publisher moves rows into a shared event log. Consumers apply each event once, in order per aggregate, and record it in the same transaction as their effect. Consumers do **database work only**: no external call ever runs inside a consumer's transaction (Law 11; ADR-005; G4 "any restart"; Part H `EventEnvelope`).

## Contracts
```python
class Outbox(OutboxWriter):   # the M4-00 port
    def __init__(self, db, *, writer: ProcessRole): ...
    def add(self, envelope: EventEnvelope) -> None            # inside the caller's transaction only
    def publish_pending(self, *, limit: int = 100) -> int     # moves unpublished rows to the event log
class Consumer:
    def __init__(self, db, *, name: str, handles: Mapping[str, Callable[[EventEnvelope], None]]): ...
    def run_once(self, *, limit: int = 100) -> ConsumerReport   # applied, duplicates, held (gaps), unhandled
```

## Rules
1. **One transaction** (Law 11). `add` raises when no transaction is open.
2. **Publishing** happens in one transaction:
   1. select unpublished rows `FOR UPDATE SKIP LOCKED`, in `(aggregate_type, aggregate_id, aggregate_version)` order;
   2. insert each into `event_log` with `ON CONFLICT (event_id) DO NOTHING`;
   3. set `published_at`;
   4. `NOTIFY investment_engine_events`.

   The insert and the mark commit or roll back together. A crashed publish therefore leaves the row unpublished, and the next run publishes it once with its **original `event_id`** (ADR-005 §6). `ON CONFLICT` covers a second publisher, or a restore that already logged the event; it is not a crash path.
3. **Consumers apply each event once.** For each `event_log` row it hasn't processed, a consumer runs the handler and inserts `(consumer, event_id)` into `processed_events` **in the same transaction**.
   - Handlers do database work only. They may record a durable work item, but never call a broker or anything outside the database.
   - A crash before the commit redelivers the event, which is applied once: this is the real duplicate-delivery boundary.
   - A handler error rolls back the effect and the mark. That aggregate is held and the error recorded; other aggregates continue.
4. **Order per aggregate** (ADR-005 §5). Versions are contiguous by construction (M4-00 rule 7). A consumer applies version n + 1 only after n. A gap holds back only that aggregate's later events. There is no global order.
5. **Event types:** exactly the M4-00 rule 7 table. Payloads are canonical JSON, with Decimal as strings; `schema_version` is 1. An unknown type is counted as unhandled and marked processed with that outcome, never silently dropped.
6. **The Execution Worker takes its submission work from the order store, not from events.** Orders still NEW are the authoritative queue (G4: "orders still NEW go through the gate"). So there is no `execution-submit` consumer, and no broker call can fall inside a consumer transaction (M4-07 rule 1). M4's consumers are the Core's order-log projection (M4-13) and the test consumers.
7. **Retention.** Published rows and the event log are kept; there is no pruning in M4.
8. **Restart.** Each process calls `publish_pending` at start-up, before any other work, and in its loop.

## Acceptance tests
- Atomicity: a failed state-change transaction leaves no outbox row; `add` outside a transaction raises.
- Publisher crash before commit (fault injection): the row stays unpublished, and the next run logs it once with the same `event_id`.
- A second publisher, and an `event_id` already in the log: one copy.
- Consumer crash after the handler, before the commit: on restart, the event is redelivered and its effect appears once.
- A failing handler holds its aggregate only; after the fix, it applies once.
- Contiguous versions: out-of-order delivery is applied in version order; a missing version holds back only that aggregate.
- The envelope round-trips exactly; an unknown type is reported as unhandled.

## Out of scope
LISTEN-based wake-ups (polling suffices), pruning, cross-database delivery.
