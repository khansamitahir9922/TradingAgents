## Goal
Run Part J's fault-injection list with the Core Engine and the Execution Worker as separate, real OS processes on PostgreSQL. This proves the crash matrix (Part E) and the recovery rules (G4) end to end (Part J fault injection; roadmap: "crash tests pass on both processes").

## Allowed files
- `tests/engine/test_fault_injection.py` (new); `tests/engine/process_harness.py` (from M4-08), extended
- `docs/tasks/M4-12.md`, `PROGRESS.md`

## Rules
1. **Scenarios** (Part J), each from a fresh database and a ReplayClock controlled by the harness:
   1. kill the Execution Worker mid-submission and mid-cancel, at the M4-08 crash points;
   2. kill the Core Engine after approval;
   3. broker timeout;
   4. a dropped database connection (M4-08 rule 6). An actual server restart isn't run: the server is the owner's shared installation. It is listed as not run, with that reason;
   5. duplicate fill;
   6. late fill after a cancel, including CANCELLED delivered before the delayed fill (M4-00 rule 4);
   7. duplicate message delivery: the M4 stand-in for Part J's "duplicate WebSocket message";
   8. stale feed: the session bar doesn't arrive, so the order expires at the cutoff with "no market data", and no fill is invented (M4-06 rule 6);
   9. a data revision mid-run: a newer revision of the decision bar before submission fails the gate's `view` check;
   10. approval expiring before submission;
   11. a concurrent cancel request and fill;
   12. the kill switch flipped between approval and submission.
   - "Missing research" is M6's (research isn't on the M4 path) and is listed as not applicable, with that reason.
2. **Each scenario asserts the end state from the stores** (order states, fill counts, broker submit counts, events, audit), together with the relevant Part J invariants from M4-11.
3. **Both processes are real.** Started through the harness from M4-08, they communicate only through the database. A failure to start a process is a test error, never a skip that counts as a pass.
4. **Time budget.** The whole file should finish within about 3 minutes on this machine. Slower scenarios are marked, never dropped.

## Acceptance tests
The twelve scenarios pass (scenario 4 as a dropped connection). Each was observed failing once against a deliberately broken build in the commit's red/green evidence, at least one per recovery rule.

## Out of scope
OS-user isolation (M7), network partitions (no network between processes).
