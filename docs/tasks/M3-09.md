## Goal
Store intent versions and drive G2 exactly, with compare-and-set writes, immutable material fields and audited transitions, proven under concurrency on PostgreSQL (Laws 10 and 12; ADR-004; ADR-008).

## Contracts
```python
ALLOWED = {   # G2, frozen; nothing else is accepted
    PROPOSED: {POLICY_REJECTED, RISK_REJECTED, SUPERSEDED, AWAITING_APPROVAL, APPROVED},
    AWAITING_APPROVAL: {APPROVED, DECLINED, EXPIRED},
    APPROVED: {CONVERTED, EXPIRED, SUPERSEDED},
}   # POLICY_REJECTED, RISK_REJECTED, SUPERSEDED, DECLINED, EXPIRED, CONVERTED are final

@dataclass(frozen=True)
class StoredIntent:
    intent: OrderIntent; state: IntentState; aggregate_version: int
    policy_decision: PolicyDecision | None; risk_decision: RiskDecision | None
    approval_deadline: datetime | None       # D11: the target session's open
    approved_by: str | None; approved_at: datetime | None; approval_expires_at: datetime | None   # D11: its close
    lineage_id: str | None

class StaleWrite(RuntimeError): ...
class IllegalTransition(ValueError): ...

class IntentStore:
    def __init__(self, db: Database, audit: AuditStore) -> None
    def create(self, intent: OrderIntent, *, by: Actor, correlation_id: str) -> StoredIntent   # idempotent by (id, version)
    def get(self, intent_id: str, version: int | None = None) -> StoredIntent                   # None: latest version
    def transition(self, intent_id: str, version: int, to: IntentState, *, expected_aggregate_version: int,
                   at: datetime, by: Actor, reason: str, **fields) -> StoredIntent
    def history(self, intent_id: str) -> list[Transition]
    def due_for_expiry(self, at: datetime) -> list[StoredIntent]
```

## Rules
1. **Compare-and-set.** One `aggregate_version` per `intent_id` covers all its versions. Each write updates it from the expected value to +1 in the same statement (`WHERE aggregate_version = expected`); zero rows means `StaleWrite` and nothing changes. Creating version N+1 also moves the aggregate, so a reduction and an approval of the old version can't both succeed.
2. **One shared state machine.** `intent_states.py` holds `ALLOWED` and the checks; the store and every caller use it. Illegal transitions raise and write nothing.
3. **Immutable material fields** (Law 12). The intent's fields are written once at create. A trigger refuses UPDATE of any material column (and of the reference and lineage columns). Only state, decisions, approval fields, lineage id and `aggregate_version` change, and each only through `transition`. Transitions are logged append-only (UPDATE, DELETE and TRUNCATE refused on the log).
4. **No orders in M3.** `transition(..., CONVERTED)` raises "orders arrive in M4" in M3, even though G2 allows it. M4's spec removes this guard through a reviewed change.
5. **Audited.** Every create and transition writes an AuditEvent in the same transaction, with before and after states.
6. **Expiry fields.** `approval_deadline` and `approval_expires_at` are set from D11 via the calendar by the pipeline (M3-12) and approval (M3-13); the store only records and queries them. `due_for_expiry(at)` returns AWAITING_APPROVAL rows with `approval_deadline <= at` and APPROVED rows with `approval_expires_at <= at`.
7. **Latest version only.** A transition on version N when version N+1 exists raises (except the SUPERSEDED move that creates N+1, done atomically).

## Acceptance tests
- Every allowed transition succeeds; every other pair, and every move from a final state, raises with nothing written (exhaustive table test).
- A stale `expected_aggregate_version` raises `StaleWrite`; state unchanged.
- **Concurrency on PostgreSQL** (two connections, real threads, a barrier): approve vs expire, approve vs decline, approve vs supersede: exactly one wins, the other gets `StaleWrite`; repeated 50 times with no lost update.
- Direct SQL UPDATE of a material column is refused; the transition log refuses UPDATE, DELETE and TRUNCATE.
- Create is idempotent for identical content and raises for a different intent under the same id and version.
- CONVERTED is refused. Each change has one audit event, rolled back with it.
