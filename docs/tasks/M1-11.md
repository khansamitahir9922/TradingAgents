## Goal
Read candles and corporate actions with DuckDB, always **for one provider**. **Every read states which view it wants:**
- the latest revisions;
- what replay may see at time T (availability);
- what this system had actually recorded by T (observation).

Reads also return **complete revision histories**, both by record and by availability window, which replay (M1-14) and explanations need.

## Contracts
Every method takes `source` (the provider) first and returns only that provider's records. **There's no cross-provider read.**
```python
class MarketDataReader:
    def __init__(self, root: Path)

    # --- Candles: one revision per identity, for bars with start_time in [start, end) ---
    def candles_latest(self, source, instrument_id, timeframe, start, end) -> list[Candle]
    def candles_visible_at(self, source, instrument_id, timeframe, start, end, at) -> list[Candle]
        # per identity: highest revision with available_from <= at; identities with none are omitted
    def candles_recorded_by(self, source, instrument_id, timeframe, start, end, at) -> list[Candle]
        # per identity: highest revision with received_at <= at   (audit view)

    # --- Candles: revision histories (every revision, not one per identity) ---
    def candle_revision_history(self, source, instrument_id, timeframe, start, end) -> list[Candle]
        # all revisions of bars with start_time in [start, end)
    def candle_revisions_available_between(self, source, instrument_id, timeframe,
                                           available_start, available_end) -> list[Candle]
        # all revisions (any bar time) with available_from in [available_start, available_end).
        # Used by replay.

    # --- Corporate actions: the same views over ex_date ranges [start, end) ---
    def actions_latest(self, source, instrument_id, start: date, end: date,
                       types: Collection[ActionType] | None = None) -> list[CorporateAction]
    def actions_visible_at(self, source, instrument_id, start, end, at, types=None) -> list[CorporateAction]
    def actions_recorded_by(self, source, instrument_id, start, end, at, types=None) -> list[CorporateAction]
    def action_revision_history(self, source, instrument_id, start, end, types=None) -> list[CorporateAction]
    def action_revisions_available_between(self, source, instrument_id, available_start, available_end,
                                           types=None) -> list[CorporateAction]
```
All `at` and `available_*` arguments must be aware UTC. Results are returned as contract objects, with Decimals preserved.

### Result ordering (total and deterministic)
Every list is sorted by a key that includes the record's **full identity plus revision**, so no two records tie and the order never depends on file or row order:

| Method | Sort key |
|---|---|
| `candles_latest`, `candles_visible_at`, `candles_recorded_by` | `(start_time)`: one revision per identity, and `source`, `instrument_id` and `timeframe` are fixed by the arguments |
| `candle_revision_history` | `(start_time, revision)` |
| `candle_revisions_available_between` | `(available_from, start_time, revision)` |
| `actions_latest`, `actions_visible_at`, `actions_recorded_by` | `(ex_date, action_type_rank)` |
| `action_revision_history` | `(ex_date, action_type_rank, revision)` |
| `action_revisions_available_between` | `(available_from, ex_date, action_type_rank, revision)` |

`action_type_rank` is the declaration order of `ActionType` (M1-09): `SPLIT` 0, `DIVIDEND` 1, `SYMBOL_CHANGE` 2, `DELISTING` 3. Ordering never uses string comparison of type names.

## Implementation choices
**Resolved**
- **No default view.** There's deliberately no `get_candles()`. ADR-009 says a missing choice is a bug, and here it can't happen.
- **`visible_at` uses `available_from`; `recorded_by` uses `received_at`.** They answer different questions:
  - `visible_at`: "what could a strategy have known at T";
  - `recorded_by`: "what did our database contain at T".
- **The provider is a required argument**, and the DuckDB queries read only that provider's partition. Mixing providers isn't expressible through this API.
- **Empty is empty.** An empty result is an empty list, never a fabricated row.

**Unresolved:** none.

## Acceptance tests (with recorded data)
**Friday correction.** A `yfinance` daily bar for Monday 2024-06-03 is stored as revision 1 (`BACKFILL_ASSUMED`, available from Monday's close). On Friday 2024-06-07 at 21:00 UTC, a corrected close is stored as revision 2 (`OBSERVED`).

| Query | Result |
|---|---|
| `candles_visible_at(at = Monday close)` | revision 1 |
| `candles_visible_at(at = Thursday 20:00 UTC)` | revision 1 |
| `candles_visible_at(at = Friday 21:00 UTC or later)` | revision 2 |
| `candles_visible_at(at = before Monday's close)` | no bar |
| `candles_latest` | revision 2 |
| `candle_revision_history` | both revisions, in order |
| `candle_revisions_available_between(Fri 00:00, Sat 00:00)` | only revision 2 |
| `candle_revisions_available_between(Mon 00:00, Tue 00:00)` | only revision 1 |

**Observation vs availability.** For a backfill imported on 2026-10-10:
- `candles_recorded_by(at = 2024-06-04)` returns **nothing**;
- `candles_visible_at(at = 2024-06-04)` returns it, labelled `BACKFILL_ASSUMED`.

**Corporate actions.**
- A dividend whose amount is corrected later behaves the same way in every view, including `action_revisions_available_between`.
- A backfilled split is visible from the start of its ex-date and not before.
- The `types` filter returns only splits when asked.
- **Same-day split and dividend.** A split and a dividend share provider, instrument, ex-date, revision 1 and `available_from`. They're written in either order, in separate imports. Every action query returns the **split first**, both times.

**Two providers.** For the same instrument and bar from `yfinance` and `testvendor`:
- every query for `yfinance` returns only `yfinance` records, and the same for `testvendor`;
- each provider's revision history is independent.

**Other cases.**
- A naive `at` raises.
- Results are sorted as specified.
- Decimals are exact.

## Out of scope
Adjusted price views, caching, cross-provider comparison (done explicitly by callers when needed).
