## Goal
Create the PostgreSQL version of the Operational Database schema, equivalent to SQLite schema 4 (M1-05, M2-07, M2-11b and the B1 guards), with the same forward-only migration rules.

## Allowed files
- `investment_engine/storage/postgres.py` (new)

## Contracts
```python
def open_operational_pg(dsn: str) -> psycopg.Connection   # autocommit off; UTC session time zone
def apply_pg_schema(conn: psycopg.Connection) -> int      # applies pending scripts; returns the version
class AppendOnlyViolation(RuntimeError): ...             # raised by the stores for refused writes (M3-02)
```

## Rules
1. **Same numbering, same meaning.** PostgreSQL version N has the tables, columns, keys and checks of SQLite version N. A later script adds to both tracks or says why it's PostgreSQL only. Each script runs in one transaction together with its `schema_version` row. A database newer than the code raises `SchemaVersionError`, as on SQLite.
2. **Native types.** Dates are `DATE`; times are `TIMESTAMPTZ`, stored and returned in UTC; record content is `BYTEA` (the same zlib bytes as SQLite); money and quantities are `NUMERIC`. The stores (M3-02) convert at the boundary, and round trips are exact.
3. **Append-only, with every PostgreSQL route covered.** Lineage and evaluation records refuse UPDATE and DELETE (row triggers) and **TRUNCATE** (statement triggers), with messages containing "append-only". A BEFORE INSERT row trigger refuses an insert whose id exists, so `ON CONFLICT DO UPDATE` and `ON CONFLICT DO NOTHING` can't replace or silently swallow a stored id. Instruments and mappings keep M1-05's rules: no delete path, and lifecycle changes only through the repository.
4. **Portable checks** from 0001 (asset class, currency length, lifecycle consistency) are copied exactly. The mapping overlap rule stays in application code inside the inserting transaction (M1-04), using `SELECT ... FOR UPDATE` on the instrument row, so concurrent inserts can't both pass.
5. Trigger functions are PL/pgSQL with fixed `search_path`; no extensions are required.

## Implementation choices
Resolved: a separate script track (`schema_pg/`) instead of one dialect-neutral file, because the trigger syntax differs and the SQLite scripts are frozen history. Resolved: `TIMESTAMPTZ` and `DATE` instead of text, for integrity; M3-03 converts on copy.

## Acceptance tests
- A fresh database migrates to 4; re-applying is a no-op; a database at 5 raises `SchemaVersionError`; a failure mid-script leaves no partial schema and no version row.
- Table and column comparison against SQLite version 4 (names, nullability, keys, checks), with the type mapping above.
- UPDATE, DELETE, TRUNCATE, `ON CONFLICT DO UPDATE` and `ON CONFLICT DO NOTHING` are each refused for an existing lineage and evaluation id; the original bytes are unchanged; a new id still inserts.
- Instrument check constraints reject the same bad rows as on SQLite.

## Out of scope
Porting the store code (M3-02), copying data (M3-03), roles and grants per process (M7).
