## Goal
A trading-enabled flag outside the database, written only by the Admin CLI, read by the Execution Worker, and treated as disabled when missing or bad. Changes to it are serialized without the database, and a halt can be made even when audit persistence fails. The record says honestly what was and wasn't applied (Law 15; ADR-006; G5; PRD §4, UC-06; D27, D28; design principles S-01 – S-03).

## Contracts
```python
@dataclass(frozen=True)
class FlagState: trading_enabled: bool; sequence: int; changed_at: datetime; changed_by: str; verified: bool; reason: str
@dataclass(frozen=True)
class FlagReading: enabled: bool; state: FlagState | None; problem: str | None   # a problem means disabled
class KillSwitchReader:
    def __init__(self, path: Path): ...
    def read(self) -> FlagReading                # never raises
@dataclass(frozen=True)
class ChangeResult:
    applied: bool; sequence: int; journal: str   # "recorded" | "FAILED: <why>"
    audit: str                                   # "recorded" | "pending (database unavailable)" | "FAILED: <why>"
```
CLI: `kill-switch status`, `halt --operator OP --reason TEXT`, `resume --operator OP --reason TEXT`, `sync-audit`.

## Rules
1. **Files** (D27), in `<data dir>/control/`:
   - `trading_enabled.json`: canonical JSON with `schema`, `trading_enabled`, `sequence`, `changed_at`, `changed_by`, `verified`, `reason` and a SHA-256 `checksum`;
   - `kill_switch_journal.jsonl`: append-only;
   - `kill_switch.lock`: the writer lock.
2. **Fail closed** (Law 15). A missing, unreadable, malformed, wrong-schema, non-boolean or bad-checksum flag reads as disabled, with a distinct `problem`. The flag starts out missing, so trading is disabled.
3. **Who** (PRD §4, UC-06; restored from v0.1). **Halt and resume are Admin-only.** The operator must be an active ADMIN, verified in the database. D31's Trader right is for cancels only.
   - **Emergency halt without verification:** if the database is unreachable, a halt is still applied, with `verified=false` and "operator identity unverified (database unavailable)".
   - **Resume always needs verification**, and is refused if the database is unreachable.
   This is not a change of permission: an unverified halt is a fail-safe stop, not a granted right.
4. **Serialized changes, without the database** (B7). Every change, and `sync-audit`, runs under an exclusive OS lock on `kill_switch.lock` (`msvcrt.locking` on Windows, `fcntl.flock` on POSIX). The OS releases it if the holder dies. Lock wait is bounded at 10 seconds, and a timeout reports who appears to hold it and changes nothing.

   **Replacing the flag is the publication point** (R2). Once `os.replace` returns, the change has happened, because a worker may already have read it. Under the lock, in this order:
   1. **Resolve outstanding intents first** (R2). For each journal INTENT with no APPLIED or NOT_APPLIED line, compare it with the **current** flag, before anything is overwritten:
      - the flag readable, with that sequence: append `APPLIED (recovered)`;
      - the flag readable, with a lower sequence: append `NOT_APPLIED`;
      - the flag readable with a **higher** sequence (possible only after an emergency halt published while an earlier resolution couldn't be journalled): the older intent stays **UNRESOLVED**, because a later flag never proves an earlier change didn't happen;
      - the flag unreadable: the outcome **can't be established**, so append `UNRESOLVED`, never NOT_APPLIED;
      - the flag readable with a sequence that has **no** INTENT line (a halt whose INTENT append failed): append `APPLIED (recovered; intent not journalled)`.
      Because this runs before every new publication, the flag that proves a change is never overwritten before that change is resolved.
   2. Allocate the next sequence: 1 + the highest sequence in the flag or in any complete journal line.
   3. Append `{"seq", "op", "phase": "INTENT", ...}` and flush.
   4. **Publish:** write a temporary file, flush it, then `os.replace` the flag.
   5. Append `{"seq", "phase": "APPLIED"}`.
   6. Release the lock, then write the audit event if the database is reachable.
5. **Failure rules** (B7, R2):

   | Failure | Halt | Resume |
   |---|---|---|
   | step 1's resolution can't be written | **still published**; reported "history incomplete: sequence n unresolved" | **refused**; nothing published |
   | step 3 (INTENT) fails | **still published**; reported `journal: FAILED`; step 1 of the next change recovers it as "intent not journalled" | **refused**; nothing published |
   | step 4 (publish) fails | nothing applied; the INTENT is resolved NOT_APPLIED next time | nothing applied; the same |
   | step 5 (APPLIED) fails, or a crash after step 4 | **applied**; reported "applied; recording incomplete"; recovered by the next step 1 | **applied**; reported the same way, **never** as refused or unchanged |
   | the audit write fails | applied; audit pending | applied; audit pending |

   A journal line never proves the flag changed; only the flag's own sequence does. History that can't be established is reported as unresolved, never invented.
6. **The journal tail.** A truncated last line, from a crash mid-append, is ignored with a warning and never counted. The next append starts on a fresh line.
7. **`sync-audit`** takes the same lock and runs step 1 first. It then writes an audit event for each APPLIED or recovered sequence missing from the audit store, keyed by sequence. A rerun adds nothing. NOT_APPLIED intents are audited as attempts; UNRESOLVED ones are listed and audited as unresolved, never as changes.
8. **Only the Admin CLI writes** (ADR-006 §2–3). `killswitch.admin` is imported only by `admin_cli.py` (layering). The worker holds only a `KillSwitchReader`.
9. **Status** shows the reading and its problem. A file the CLI can't read is shown as "TRADING DISABLED: <problem>", never guessed. Pending audit and unverified halts are listed.

## Acceptance tests
- Each fail-closed case gives disabled, with its problem.
- Roles: an Admin halts and resumes; a Trader and a Viewer are refused both, with the database up; with the database down, an unverified halt applies, and a resume is refused.
- Two writers in separate processes, 20 repetitions: distinct, increasing sequences, never the same number twice.
- Crash at each boundary (after INTENT, after the flag replace, after APPLIED, before the audit), with recovery checked each time.
- **R2, each row of the failure table** for both halt and resume: INTENT and APPLIED appends failed independently. Resume with a failed APPLIED reports "applied", never refused.
- **The higher-sequence case:** an older INTENT whose resolution journalling failed, overwritten by a permitted emergency halt, stays UNRESOLVED; it is never NOT_APPLIED.
- **R2, overwrite safety:** a halt publishes sequence 7 and crashes before APPLIED; another change runs before `sync-audit`. Step 1 records 7 as APPLIED (recovered) before 8 is published, and `sync-audit` then shows both changes honestly. With the flag unreadable at step 1, the intent is recorded UNRESOLVED and a resume is refused.
- A truncated journal tail is ignored; `sync-audit` is idempotent; NOT_APPLIED is never audited as a change.
- Layering: no module except `admin_cli.py` imports `killswitch.admin`.
