## Goal
The worker's step:
- gate and submit new orders, with the broker call **outside** every database transaction;
- ingest broker messages exactly once, following the M4-00 matrix;
- carry each cancel request to a durable close, with retries, even while trading is disabled.

Every write is a compare-and-set with its event (G1 steps 11–14; Laws 13–15; G3).

## Rules
1. **Submission, in three phases** (Law 14; B3). The work queue is the order store's NEW orders (M4-01 rule 6).
   1. **Gate transaction** (M4-05 rule 4): the locks, fresh reads, the decision, then NEW → SUBMITTING or GATE_REJECTED; **commit**.
   2. **Broker call, outside any transaction:** `broker.submit`.
   3. **Outcome transaction**: ACCEPTED gives SUBMITTING → SUBMITTED, with the broker order id. A definite REJECTED gives SUBMITTING → REJECTED. A `BrokerTimeout`, or any error leaving the outcome unknown, gives SUBMITTING → UNKNOWN. Whatever happens, the order is never resubmitted.

   A crash between phases leaves SUBMITTING, and recovery resolves it (M4-08).
2. **Message ingestion** (B1). This runs in the worker's ingest loop, not an event consumer. Each broker message is applied in its own transaction, together with the advance of the stored broker cursor. The effect follows the M4-00 rule 4 matrix, and for the other kinds this table:

   | Message | Order state | Effect |
   |---|---|---|
   | ACK | SUBMITTING, UNKNOWN | → SUBMITTED |
   | ACK | anything later | duplicate or out-of-order: no change |
   | FILL | any | the M4-00 rule 4 matrix |
   | CANCELLED | CANCEL_PENDING | → CANCELLED |
   | CANCELLED | SUBMITTED, PARTIALLY_FILLED (unsolicited) | → CANCEL_PENDING → CANCELLED, two edges |
   | CANCELLED | UNKNOWN | → CANCELLED (resolution) |
   | CANCELLED | already final | no change |
   | EXPIRED | SUBMITTED, UNKNOWN | → EXPIRED |
   | EXPIRED | PARTIALLY_FILLED, CANCEL_PENDING | **no G3 edge**: recorded as an anomaly, the state unchanged (D19); the simulator never sends this |
   | REJECTED | SUBMITTING, SUBMITTED, UNKNOWN | → REJECTED |
   | REJECTED | anything later | anomaly |

   A message whose `message_id` was already applied is skipped. Every versioned effect changes the order's version and emits its one event; anomalies add audit only (M4-00 rules 7, 9). Fill and terminal writes take the account-control lock first (M4-05 rule 4).
3. **Cancels, with durable progress** (B2; D31). For each cancel request not CLOSED, each step:
   - order NEW: the gate's `cancel` check rejects it (GATE_REJECTED), then CLOSED / NOTHING_TO_CANCEL;
   - order SUBMITTED or PARTIALLY_FILLED: in one transaction, → CANCEL_PENDING and progress SENDING (attempt n); commit; call `broker.cancel` outside any transaction; then record the result. **CANCELLED or PENDING gives SENT**, with the broker's `received_at`. TOO_LATE is recorded and waits for the order's final state. A timeout leaves it SENDING. A PENDING result is **never** treated as cancelled: the request stays SENT until the CANCELLED or FILL message makes the order final (R1);
   - order **already CANCEL_PENDING** (after a crash or a timeout): **send `broker.cancel` again**, recording attempt n + 1. The broker treats a repeated cancel for the same `client_order_id` idempotently. At most one attempt per step.
   - order in a final state: CLOSED with an outcome that reflects it (CANCELLED, or TOO_LATE when it filled or expired).

   A request is closed only when the order reaches a final state; saving CANCEL_PENDING is never treated as cancelled. All of this runs whatever the kill switch says (Law 15).
4. **UNKNOWN orders** are looked up each step (M4-08 rule 3).
5. **Order within a step:** publish pending; ingest messages; cancels; UNKNOWN lookups; then new submissions. Fills and cancels come before new risk.
6. A `StaleWrite` aborts only that order's work for the step, and the next step re-reads.

## Acceptance tests
- Happy path: NEW → SUBMITTING (committed) → `submit` → SUBMITTED, then a fill and FILLED, with contiguous versions and events.
- Phase boundaries: a test double that checks, at the moment `submit` is called, that SUBMITTING is already committed (read on another connection). The broker is never called inside a transaction.
- A gate failure means zero `submit` calls. A timeout gives UNKNOWN, and later steps never call `submit` again.
- The ingestion table row by row, including the two-edge unsolicited cancel; partial fills, then a completing one; CANCELLED delivered before a delayed fill (M4-00 rule 4); duplicate and reordered messages.
- Cancels: a timeout leaves SENDING and the next step resends; an order already CANCEL_PENDING is resent; TOO_LATE after a fill closes the request; with trading disabled, a cancel still goes through to CANCELLED.
- A cancel request racing a fill (PostgreSQL, 20 repetitions): the final state is FILLED or CANCELLED, with one fill and a closed request.

## Out of scope
Start-up recovery (M4-08), positions (M4-09).
