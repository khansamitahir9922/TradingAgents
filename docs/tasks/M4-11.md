## Goal
Test every Part J order invariant as a property over many seeded random sequences of events, across the real stores, the gate, the worker and the simulator or a broker double (Part J; ADR-004 "How we check it"; roadmap: "every Part J order invariant is tested"; D33).

## Allowed files
- `tests/engine/test_order_invariants.py` (new), `tests/engine/order_sequences.py` (new, test-only): a seeded generator of proposals, approvals, conversions, gate inputs, broker messages (including partial fills, CANCELLED before a delayed fill, identical and conflicting duplicate fills, and reordered acks), cancels and cancel retries, kill-switch flips, timeouts and crashes
- `docs/tasks/M4-11.md`, `PROGRESS.md`

## Rules
1. **Plain pytest, seeded** (D33). Each property runs N seeded sequences: N = 200 by default, and more under an opt-in marker. A failure prints its seed, so it can be replayed exactly. No new dependency.
2. **The invariants, each its own test** (Part J, the order rows):
   - rejected intents never become orders;
   - a REJECTED or GATE_REJECTED order never becomes FILLED;
   - duplicate broker messages never create duplicate fills, and a conflicting duplicate is refused as an anomaly;
   - UNKNOWN orders are never resubmitted: the broker double counts submits per `client_order_id`;
   - nothing new is submitted while the kill switch is off or unreadable, and cancels still pass;
   - an approved intent version never changes;
   - a stale compare-and-set write on an order always fails;
   - every order aggregate's event versions are contiguous, one per write (M4-00 rule 7);
   - every cancel request reaches CLOSED once its order is final, with trading enabled or disabled;
   - each order transition is written only by its owning process;
   - no path reaches the broker without Policy, Risk and the Gate: every `submit` call has an APPROVED → CONVERTED intent with recorded policy and risk decisions, and a passed gate decision;
   - no process other than the Execution Worker can load broker credentials (the M4-03 test, linked here).
   - The ledger invariants are M5's.
3. **Replay determinism** (Part J replay tests). The same data and versions give the same views, intents, orders, fills and ids, across two runs.
4. **Each invariant is checked against the stores' final state and history**, never against what the code believes it did.

## Acceptance tests
The rule 2 tests and the rule 3 test pass. Each invariant test also has a deliberately broken variant, run once in the commit's red/green evidence (not kept), which shows that the test can fail: for example, a worker patched to resubmit UNKNOWN orders.

## Out of scope
The two-process fault matrix (M4-12), ledger invariants (M5).
