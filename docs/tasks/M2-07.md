## Goal
Run the view pipeline on each closed daily bar from the replay feed:
- adjusted view, features and snapshot;
- strategies and policy, giving a MarketView;
- record a **LineageRecord** that explains the view completely (Part H; Part F "Lineage").

Lineage is append-only (Law: history is never overwritten) and stored in the SQLite operational database (ADR-008: SQLite through M2).

## Contracts
```python
@dataclass(frozen=True)
class LineageRecord:
    lineage_id: str                       # deterministic: hash of the content below
    instrument_id: str; generated_at: datetime
    bar_refs: tuple[BarRef, ...]           # complete feature and health input identities
    action_refs: tuple[ActionRef, ...]
    action_coverage: ActionCoverage       # including verified-empty coverage evidence
    feature_versions: Mapping[str, str]
    strategy_versions: Mapping[str, str]
    policy_version: str
    data_health: DataHealth               # full immutable result, reasons, age, gaps, T
    health_thresholds: HealthThresholds
    snapshot: FeatureSnapshot            # values and unavailable/warm-up reasons
    signals: tuple[StrategySignal | None, ...]
    decision: MarketView                  # before adding evidence_refs; includes ABSTAIN
    config: Mapping[str, object]          # validated immutable policy/feature parameters
    calendar_version: str
    code_version: str                     # investment_engine.__version__ plus the git commit if known
    research_run: None; model_version: None; portfolio_snapshot: None; risk_versions: None   # later milestones

class LineageStore:                       # append-only over the operational DB
    def append(self, record: LineageRecord) -> None    # idempotent for an identical record; a different record under the same id raises
    def get(self, lineage_id: str) -> LineageRecord

def run_views(feed: ReplayFeed, ...) -> Iterator[MarketView]   # one view per BAR_CLOSED D1 event of the instrument

class ReplayKnowledgeReader:
    # Ephemeral reader projection, not a store: only revisions actually delivered by this feed.
    def accept(self, event: ReplayEvent) -> None
    def candles_visible_at(self, source, instrument_id, timeframe, start, end, at, *, through_sequence=None) -> list[Candle]
    def actions_visible_at(self, source, instrument_id, start, end, at, types=None, *, through_sequence=None) -> list[CorporateAction]
```

## Rules
1. **Trigger:** a view is produced at each `BAR_CLOSED` D1 event for the instrument, with `T = event.received_at`. `CANDLE_REVISED` and `CORPORATE_ACTION` events don't produce views in M2. A later view reads the corrected data as of its own T.
2. **Complete lineage:** every feature and health input revision, action/coverage evidence, parameters, full DataHealth and decision context. Health inputs can be gathered by the same explicit PIT read/window used by M1-16; this task does not require changing its public contract. Snapshot versions and recorded calendar/threshold versions allow the reason for a view to be reconstructed, including an ABSTAIN with no bars. Hash canonical JSON with UTC times, Decimal strings and sorted immutable mappings; exclude the lineage ID and returned view's evidence references.
3. **Append-only:** the API has no update/delete path. Schema triggers reject UPDATE and DELETE of lineage rows; direct SQL regression tests prove it. Existing M1 tables are unchanged. Use the existing numbered-schema loader; schema expectations in its allowed test file are updated without dropping previous assertions.
4. **Determinism:** two replays give the same views and the same lineage ids.
5. **Latency cannot leak through a second read.** Before producing a view, accept the current event into `ReplayKnowledgeReader`; all features and health use this reader, not the unrestricted store. A revision is eligible only if its event has already been delivered at T as well as satisfying the ordinary PIT query. With latency 5 seconds, a correction available at E+3 cannot enter a view at E+5; it first becomes known when delivered at E+8. Equal-time events follow the feed sequence. The projection is scoped per provider/full identity and selects the highest delivered revision, without modifying stored timestamps or adding an authoritative store. **Since Codex finding B2 (2026-10-15):** each revision keeps its delivery time and feed sequence; a query at T sees a revision only if it is available and delivered by T, so a later historical re-query gives the same answer. `through_sequence` keeps equal-time events in feed order.
6. Start the feed early enough to deliver all necessary warm-up bars/actions. There is no hidden preload of final revisions or latest-store snapshot; an insufficient feed gives explicit warm-up/unavailable output. Versioned action-coverage evidence supplied to a research run is labelled separately from observed action events.

## Implementation choices
**Resolved:**
- No separate authoritative MarketView store is introduced. The immutable decision content is recorded in lineage; reports can read that content or deterministically regenerate it from the referenced inputs.
- Fields for later milestones are present and `None`, so the contract keeps one shape.
- `code_version` is an explicit caller-supplied build/version identifier, required for reportable runs; don't spawn git or read the clock inside business logic. Synthetic tests pass a labelled test version.

**Unresolved:** none.

## Acceptance tests
- A view's lineage lists exactly the bars and actions used; a correction available after T isn't in it.
- An identical append is a no-op; a conflicting append raises; there's no update or delete path.
- The schema migration 0002 applies to an existing M1 database without touching its tables.
- Determinism across two replays.
- Latency regression: revision 1 available at E, revision 2 at E+3, latency 5 seconds. The view at E+5 uses only revision 1 in features, health and lineage; revision 2 is usable only after its E+8 delivery. Reversed reader order and equal-time feed sequences cannot change this.
- An ABSTAIN view still has full lineage, including the DataHealth that caused it.
- Changing the calendar version, threshold configuration, feature parameters or decision content changes the hash. Returned evidence references point to the stored context without hash recursion. Direct SQL mutation is refused.

Lineage content is canonical tagged JSON, stored zlib-compressed; ids are `lin-` + SHA-256. Health inputs use M1-16's `_lookback` window. A registered dataclass may list `LINEAGE_LATER_FIELDS`: fields added after records were stored, omitted from the encoding while `None` so historical payloads and ids are unchanged (R1). No lineage class uses it, so lineage ids are unaffected. Migration 0004 (B1) adds insert guards to the append-only table.
