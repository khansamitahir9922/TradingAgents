## Goal
Run G1 steps 6–9 for one account and one view: snapshot, sizing, policy, risk, any reduction, then approval routing by autonomy level, with every decision reconstructable and replay-deterministic (Laws 5, 9, 12, 18; Part J replay test).

## Contracts
```python
@dataclass(frozen=True)
class IntentLineageRecord:
    intent_id: str; version: int; view_lineage_id: str; snapshot_id: str
    autonomy: AutonomySetting; policy_version: str; risk_version: str; sizer_version: str
    reference_bar: BarRef; adv_refs: tuple[BarRef, ...]
    policy_decision: PolicyDecision; risk_decision: RiskDecision
    calendar_version: str; code_version: str
    lineage_id: str = field(init=False)      # "ilin-" + SHA-256 of canonical content

class ProposalOutcome(StrEnum):
    NO_INTENT; POLICY_REJECTED; RISK_REJECTED; AWAITING_APPROVAL; APPROVED; SNAPSHOT_UNAVAILABLE

@dataclass(frozen=True)
class ProposalRecord:                         # one per (account, view): what happened and why
    account_id: str; view_lineage_id: str; at: datetime; outcome: ProposalOutcome; reason: str
    intent_id: str | None; final_version: int | None; record_id: str = field(init=False)   # "prp-" + SHA-256

@dataclass(frozen=True)
class ControlStores:                          # one Database; every store joins the caller's transaction
    db: Database; audit: AuditStore; accounts: AccountRegistry; limits: LimitStore
    snapshots: PortfolioSnapshotStore; intents: IntentStore; lineage: LineageStore
    intent_lineage: IntentLineageStore; proposals: ProposalStore

def propose(account_id: str, view: MarketView, *, at: datetime, stores: ControlStores, reader, calendar,
            coverage, calendar_version: str, code_version: str, correlation_id: str) -> ProposalRecord
def expire_due(*, at: datetime, stores: ControlStores) -> list[StoredIntent]
# IntentLineageStore (lineage/intent_lineage.py) and ProposalStore (oms/pipeline.py): append-only,
# append (identical is a no-op, conflicting raises) and get by id, like M2-07's LineageStore.
def propose_over_replay(account_id: str, views: Sequence[MarketView], *, latency: timedelta, ...) -> list[ProposalRecord]
```

## Rules
1. **Order of work.** Expire due intents first (`expire_due(at)`). Then load the account, its autonomy at `at`, limits and rules at `at` (missing ones mean a rejection with the reason), and the view's LineageRecord (M2-07). Build and store the snapshot (unavailable gives `SNAPSHOT_UNAVAILABLE`), then size. No intent gives `NO_INTENT` with the sizer's reason (ABSTAIN, NEUTRAL, already at target, below one share).
2. **Checks.** Create v1 PROPOSED, then policy. A failure is POLICY_REJECTED. Then risk: REJECT is RISK_REJECTED; REDUCE marks v1 SUPERSEDED and creates v2, which runs policy and risk again (M3-11 rule 3); a HaltRequest records the latched halt.
3. **Routing by autonomy** (B3, G2). Level 1 goes to AWAITING_APPROVAL with `approval_deadline` = the open of `target_session` (D11). Level 2 goes to APPROVED with `approved_by` = PROCESS `core-engine` ("Level 2 rule"), `approved_at = at` and `approval_expires_at` = the close of `target_session`, but never later than the view's `valid_until` (D10, D11). If `at` is already past the deadline, the intent goes to EXPIRED with the reason.
4. **Atomic and audited.** Everything for one (account, view) commits in one transaction: snapshot, intent versions, transitions, decisions, halt, intent lineage, ProposalRecord and audit events. A failure leaves nothing.
5. **Idempotent.** Re-running `propose` for the same account and view returns the stored ProposalRecord and changes nothing. The intent id is deterministic (M3-08 rule 1).
6. **Lineage.** Each final intent version gets an IntentLineageRecord linking its view lineage (unchanged; M2's `LineageRecord.portfolio_snapshot` and `risk_versions` stay None, because they describe the view), its snapshot, decisions and versions. It's stored append-only and set as the intent's `lineage_id`.
7. **Replay.** `propose_over_replay` runs views in time order, with `at = view.generated_at + latency` (default 0) and a ReplayClock, against one research account. M3 has no fills, so holdings stay at the declared start. This is stated in every output. Two runs into fresh databases give identical ProposalRecords, intents, decisions and lineage ids.
8. **No orders, no outbox** (M3 README). Nothing here touches broker code or credentials.

## Acceptance tests
- Each path end to end on PostgreSQL: NO_INTENT (ABSTAIN, NEUTRAL), SNAPSHOT_UNAVAILABLE, POLICY_REJECTED (Level 0; PAPER promotion), RISK_REJECTED, REDUCE then AWAITING_APPROVAL (v1 SUPERSEDED, v2 waiting), Level 2 APPROVED, already-expired.
- Atomicity: a failure injected after the decisions leaves no intent, snapshot, lineage, record or audit event.
- Idempotent re-run; daily buy cap across several views on the same session.
- Expiry: AWAITING_APPROVAL past the open and APPROVED past the close move to EXPIRED with audit events.
- Replay determinism across two fresh databases (ids and decisions equal); lineage reconstructs every decision input.
- No import of broker, kill-switch or outbox code (an import scan in `test_intent_pipeline.py`).
