## Contracts

## Rules
1. **The port owns transactions** (Codex S1). Both connections run in autocommit mode, so a read outside `transaction()` never opens an implicit driver transaction. `transaction()` opens one managed transaction: SQLite `BEGIN IMMEDIATE`; on PostgreSQL, psycopg's `Connection.transaction()` at the outermost level. A nested `transaction()` joins the outer scope: no savepoint, and a failure inside it rolls back the whole outermost transaction. The adapter tracks the nesting depth; `in_transaction` reports the managed scope, never the driver's own status. Store write methods open a managed transaction if none is open, and otherwise join the caller's.
2. **One store, two backends.** SQL uses named `:name` parameters. `PostgresDatabase` translates them to `%(name)s` with a strict pattern that ignores `::` casts and string literals. Statements are constants in the code, never built from input. Records, ids, errors and refusals are identical on both backends.
3. **Errors are the same type.** Append-only refusals raise `AppendOnlyViolation` on both backends. Conflicts keep `LineageConflict` and `EvaluationRunConflict`. Driver exceptions don't leak through store methods.
4. **R1 and B1 stay true on PostgreSQL.** The genuine `57d4316` evaluation record reads back under its original id on both backends. Every replacement route is refused.
5. **SQLite is legacy and test-only** (Codex review answer 2; ADR-008). PostgreSQL is the only operational database from M3: the CLI (M3-03) and every M3 store use it, and all M3 concurrency and transaction acceptance runs on it. The SQLite adapter remains:
   - for reading existing files (M3-03's copy);
   - for the dual-backend tests of the M1–M2 stores and historical formats;
   - for M2's external offline report script, which builds a throwaway file.

   There's no compatibility shim for raw `sqlite3.Connection` callers and no promise of writable SQLite for old notebooks. Callers in the repository are updated to `SqliteDatabase` in this task.
6. **Symbol mappings under concurrency** (Codex B4): mapping inserts take M3-01 rule 4's two advisory locks in key order inside the inserting transaction, then check `conflict` and insert. On SQLite, `BEGIN IMMEDIATE` already serializes writers.

## Implementation choices
Resolved: a thin port rather than an ORM, which would add a dependency and hide SQL. Resolved: existing class names are kept to avoid churn; renaming is cosmetic and left out.

## Acceptance tests
- Every existing store test passes on both backends; the count per backend is reported.
- Parameter translation: names, repeated names, `::` casts, quoted `:text` and an unknown name (raises).
- **Transactions (S1):** after a read, `in_transaction` is False and another connection sees a committed write immediately; a write inside `transaction()` is invisible to another connection until the outermost scope exits; a failure in a nested scope rolls back the outer writes too; a store write inside the caller's scope commits with it.
- **Mapping races on PostgreSQL (B4):** two connections with a barrier, 50 repetitions each:
  - the same provider and symbol mapped to different instruments for overlapping dates, with no prior mapping row;
  - the same instrument mapped to different symbols for overlapping dates.

  In each case exactly one commits. Non-overlapping reuse of a symbol, and the same symbol at a different provider, both commit.
- Old-format and current-format evaluation records, and lineage records, round-trip identically on both backends.
