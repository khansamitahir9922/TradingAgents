## Goal
Part H requires **raw (unadjusted)** prices. Yahoo describes its historical "Close" as adjusted for splits, and "Adj Close" as adjusted for splits and dividends. yfinance's `auto_adjust=False` therefore **doesn't prove** anything about the values.

This task:
1. **Determines from evidence what each field actually means**, separately for:
   - daily prices, daily volume, hourly prices and hourly volume;
   - dividend amounts and split ratios.
2. **Chooses each field's transformation from that evidence.** There's no single hypothesis that everything must satisfy.
3. Documents the evidence and the precision limits.
4. **Only for fields whose semantics are established**, imports NVDA's splits and dividends as CorporateActions.

Reconstructed values can satisfy Part H's "unadjusted" requirement when the reconstruction is independently verified (accepted in Codex review).

## The complete split history
Every reconstruction uses `F(d)`: the product of split ratios with `d < ex_date <= download date`, for `d >= verified_from` only (below). **All** splits after `d` count, including splits after the requested window. "Complete" in this spec and in M1-13 means complete **over the verified date range**: every vendor split with `ex_date >= verified_from`, checked against `cited_splits`. Rules:
- **Full history only.** yfinance's `history(start, end, actions=True)` reports only events inside the requested dates, so it must **never** be the source of `F`. The split history comes from a **full-history** request (e.g. `Ticker.splits`, or `history(period="max", actions=True)`). The task records which call is used, and the integration check confirms that the call isn't date-filtered.
- **Same adjustment basis.** Within one import run, the split history is fetched **immediately before and after** the data download. If the two differ (a split landed mid-run), the run aborts.
- **Completeness is checked** against `cited_splits` (evidence S below) over the verified date range, which contains every date any import may cover.
- **Agreement with storage.** Before bars are imported (M1-13), the split history must equal the stored `yfinance` `SPLIT` actions (`actions_latest`, M1-11), or the import aborts. **v0.3.1:** both sides are compared over the verified range only (below).

### Verified date range (v0.3.1; shared with M1-13)
The evidence covers one explicit range, recorded in `YAHOO_VERIFICATION`:
- **`verified_from`:** the first date any import may cover. For NVDA it's **2019-01-01**.
- **`cited_splits`:** every split with an ex-date on or after `verified_from`, each with its cited ratio and ex-date (evidence S).

The range is enforced, not just documented:
1. **Requests before the range are refused before any fetch.** A bar import with `start < verified_from` raises, and nothing is fetched or written. Otherwise a caller asking for older bars could reconstruct them with split history containing unverified dates.
2. **Vendor splits inside the range must equal `cited_splits` exactly**, same ex-dates and same ratios. That includes splits **after the requested window** and after `verified_on`. An extra split, a missing one or a different ratio aborts the import. A **new** split since verification therefore stops every import until its citation is added and reviewed.
3. **Vendor splits before the range are never used and never stored.** For any `d >= verified_from`, `F(d)` takes only splits with `d < ex_date <= download date`, all inside the range. Earlier splits are reported by the action import as *outside the verified range*.
4. **Every later split stays in `F`.** Restricting the range never drops a split after `d`, including splits outside the requested window. It only excludes splits that can't affect any allowed date.
5. **Storage agreement compares the verified range on both sides:** the vendor's splits with `ex_date >= verified_from`, against the stored `yfinance` `SPLIT` actions with `ex_date >= verified_from`.
6. **`split_factor` enforces it too (v0.3.2).** It raises for `d < verified_from`, and for any split passed to it with `ex_date < verified_from`, so no caller can compute `F` from unverified history. Dividends follow the same range: only `ex_date >= verified_from` is imported.

*Why: Yahoo dates NVDA's 2001 split 2001-09-12. US markets were closed that day, and the actual ex-date isn't established. Under the v0.3 rule, that one unverifiable old split would have blocked every import.*

## Field-by-field determination
Each field is decided **separately**. For each one, the result is one of:
- `UNADJUSTED`;
- `SPLIT_ADJUSTED_AS_OF_DOWNLOAD`;
- `OTHER` (e.g. dividend-adjusted);
- `UNDETERMINED`.

The transformation follows from the result:

| Result | Transformation | Stored basis |
|---|---|---|
| `UNADJUSTED` | identity | `RAW_AS_REPORTED` / `AS_REPORTED` |
| `SPLIT_ADJUSTED_AS_OF_DOWNLOAD` | split reconstruction (below) | `RAW_RECONSTRUCTED_FROM_SPLIT_ADJUSTED` / `RECONSTRUCTED_FROM_SPLIT_ADJUSTED` |
| `UNDETERMINED`, but **primary evidence** shows the field is at most split-adjusted (e.g. not dividend-adjusted), and it's consistent with the daily data | identity **only where `F(d) == 1`** (no split between bar and download, so the value is the same either way) | `RAW_NO_LATER_SPLIT` / `NO_LATER_SPLIT` |
| `OTHER`, or `UNDETERMINED` otherwise | **none: the field is blocked** | — |

**Reconstruction** (only for `SPLIT_ADJUSTED_AS_OF_DOWNLOAD` fields):
```
price(d)    = vendor_price(d) × F(d)       → quantize PRICE_QUANTUM, half-even
volume(d)   = vendor_volume(d) ÷ F(d)      → quantize SHARE_QUANTUM
dividend(e) = vendor_dividend(e) × F(e)    → quantize PRICE_QUANTUM
```
Using splits that happened *after* d is **not look-ahead**: it undoes the vendor's later adjustment to recover values actually traded on d.

### Daily volume rule (V-D, v0.3.1)
Daily volume is **established** for a candidate interpretation only when **all** of these hold:
1. **Decisive anchors:** at least one cited as-traded daily volume for a session with `F(d) > 1`. Only these can tell the interpretations apart, because the candidates differ by the factor `F`.
2. **Every** selected decisive anchor is within **3%** of the vendor value under that interpretation. The candidate's value is `vendor_volume(d)` for `UNADJUSTED`, or `vendor_volume(d) ÷ F(d)` for `SPLIT_ADJUSTED_AS_OF_DOWNLOAD`. All decisive anchors are listed, with none dropped after the comparison.
3. Under the **other** interpretation, every decisive anchor is off by **at least 50%**.
4. **Control checks are recorded:** sessions after the last split (`F = 1`) from the same reference source. They measure the reference-to-vendor gap (venue coverage, late trades), but they **can't distinguish the interpretations** and never count as decisive. A control gap above 3% is investigated and recorded before any decision.

If any condition fails, daily volume is `UNDETERMINED` and **blocked**. The 3% limit, every anchor's error, the wrong interpretation's error and the control gaps are recorded in the provenance document.

### Hourly volume rule (V-H, v0.3.1)
Hourly volume is decided **separately** from daily volume. A daily result never establishes it, and the daily 3% limit never applies to it. Comparing the **sum** of hourly bars with a daily volume can't establish hourly semantics, because the two may cover different trading hours and different trades. A difference doesn't identify its cause. Hourly volume is **established** only by one of:
- **(a) Comparable independent hourly references:** cited as-traded hourly volumes for bars with `F(d) > 1`. Each reference states, or documents, the **same bar boundaries and session** as the vendor's hourly bars (regular-session hours, `America/New_York` bar starts, the same treatment of the opening and closing auctions and late trades). Each must be within **3%** under exactly one interpretation, with the other off by at least 50%. Control bars (`F = 1`) are recorded as for daily volume.
- **(b) Explicit provider documentation** stating whether intraday volume is split-adjusted, quoted with link and retrieval date.

Without (a) or (b), hourly volume is `UNDETERMINED` and **blocked**. That includes the `F == 1` exception. The hourly-sum ratios against daily references are recorded as **supporting evidence only**.

### Why dollar-volume continuity can't decide (counterexample)
Consider a 4:1 split, with real trading activity rising around it:

| | Before split | After split |
|---|---|---|
| As-traded price | 40 | 10 |
| As-traded volume (the truth) | 1,000 | 16,000 |
| Vendor volume (split-adjusted: before × 4) | 4,000 | 16,000 |

Testing the two candidates, with prices reconstructed to as-traded:
- **"Vendor volume is unadjusted" (identity):** dollar volume 40 × 4,000 = 160,000 before, and 10 × 16,000 = 160,000 after. **Ratio 1.0, so it looks perfectly continuous.**
- **"Vendor volume is split-adjusted" (reconstruct ÷ 4):** 40 × 1,000 = 40,000 before, and 160,000 after. Ratio 4.0.

The heuristic favours identity and would store **4,000 shares where 1,000 were traded**. Genuine changes in activity around a split (common, since splits often follow strong price moves) look exactly like an adjustment. Hence the rule: **continuity is supporting evidence only**, and a cited anchor of 1,000 shares, or explicit documentation, is what establishes the basis.

### Precision limits (documented, not hidden)
The provenance document records, per field:
- the vendor's delivered precision (observed decimal digits, and the float representation);
- the resulting bound on reconstruction error (≈ `F × vendor rounding unit`);
- the measured maximum error against anchors;
- a statement of which stored digits are significant.

The stored quantum (`0.0001`) can be **finer than the information** in a reconstructed value. The report (M1-17) points to this note.

*Field-update algorithm* (one bar). Trades are taken in (SIP timestamp, delivery order) and the rule's validity filter is applied:
- **Open/close.** An *all* trade sets close, and open if open is unset. A *first-only* trade does the same only if it is the bar's first, under the rule's fixed reading. Two readings are defined:
  - **first-trade:** the bar's first valid trade of any condition. This is Alpaca's wording, "the first trade of the bar"; it never arises in minute bars.
  - **no-open-yet:** no earlier trade in the bar has set open/close. This is the UTP wording, per bar; H-DAY uses it.

  A *none* trade never sets them. **If no trade sets open/close, they stay unset.**
- **High/low.** Max and min over trades whose high/low effect isn't *none*.
- **Volume.** The sum of sizes of trades whose volume effect isn't *none*. The count follows the definition fixed at A2.
- **Existence.** A bar exists (Alpaca emits it) only if open, high, low and close are all set and volume > 0.

D-OFFICIAL evaluates **only high/low and volume**. Official open/close have further rules (e.g. the 16:00:10 last-sale cutoff, UTP note 2) that this protocol doesn't need.

*Validity and cancellation evidence.*
- Alpaca's historical-trades reference documents an optional `u` field: "if it's missing, the trade is valid", otherwise `canceled`, `incorrect` (corrected, so no longer valid) or `corrected` (the correction of an incorrect trade).
- **Alpaca staff confirm it for historical trades** (Alpaca community forum, "Persistent IONQ SIP trade/bar mismatch: 2 trades and 2 shares", reply by Dan_Whitnable_Alpaca, 2026-07-16; retrieved 2026-10-12): "There is a field labeled `u` in the JSON response which indicates if that trade was subsequently canceled or corrected", and "Trades that are `canceled` or `incorrect` are not included in bar calculations however, they do show up as trades." The official Python trade model omits the field, and the real-time feed sends separate messages; neither changes the historical response. **Codex's objection is resolved.**

The validity rule is pre-registered: `canceled` and `incorrect` are excluded; `corrected` and unflagged records are included. That is also Alpaca's own bar rule, so reconciliation uses it. Then:
- **H-UNCANCELLED** (`canceled` and `incorrect` kept) is **testable only if** the pulled historical data contains at least one flagged `canceled` or `incorrect` record. Otherwise every H-UNCANCELLED result is **untestable**. Without flags, H-MIN and H-UNCANCELLED would be identical and would test nothing. Untestable never counts as explained.
- Even when testable, an H-UNCANCELLED explanation needs the specific trade setting Yahoo's extreme to **carry** the flag. The absence of a flag never proves a trade wasn't cancelled.
- If cancelled trades are silently removed, or silently kept without flags, D-OFFICIAL may fail to reproduce Yahoo's daily extremes. Those differences then stay unexplained, which fails safe.

*Timestamps and boundaries.*
- **Minutes**, for reconciliation, are the SIP timestamp **truncated to the minute**, as Alpaca does. Nothing is reassigned: a closing-cross print at 16:00:00.2 is in the 16:00 minute.
- **Hourly bars** are `[09:30 + k h, min(09:30 + (k+1) h, close))` in `America/New_York`, by SIP timestamp (`t`, parsed exactly from RFC 3339 with nanoseconds). Sessions and closes come from the cited calendar. Trades before the open, and trades at or after the close, are in no hourly bar, except under the CC-LAST hypothesis.
- **CC-LAST (a Yahoo hypothesis, separate from reconciliation):** every closing-cross print (condition 6) on the session's trading date with a timestamp at or after the close belongs to the session's **last** hourly bar. **Capture boundary:** `[close, 24:00 New York)` of the trading date, always pulled completely: within the full-date pull, or, for volume-only sessions, as its own pull with paging integrity. Reports dated later are out of scope, and that limitation is recorded. **CC-TS** is the alternative: timestamps only, and no print at or after the close is in any bar. The two are always evaluated as separate hypotheses, for prices and for volume.

*The hourly rules* (eight combinations: each base rule with CC-TS and with CC-LAST; one combination must be selected):

| Base rule | Profile and reading | Validity | Hypothesis |
|---|---|---|---|
| **H-MIN** | ALPACA | flagged excluded | Yahoo follows the documented intraday rule |
| **H-ODD** | ALPACA, but an odd-lot condition (I) **alone** no longer stops a trade setting high/low. A trade with another blocking condition stays excluded; open/close and volume unchanged | flagged excluded | odd lots set Yahoo's hourly extremes |
| **H-DAY** | UTP within each hour, no-open-yet reading | flagged excluded | Yahoo applies official daily eligibility intraday |
| **H-UNCANCELLED** | ALPACA | flagged **kept**; testable only with flag evidence | Yahoo didn't apply later cancellations |

*The official daily rule:* **D-OFFICIAL**, the UTP profile over **every trade of the session's trading date** (00:00 – 24:00 New York), with flagged trades excluded. Late and extended-hours reports are judged by their conditions (e.g. T, U and Z), not their times. It must reproduce Yahoo's daily high or low within $0.01 (Yahoo's daily values are treated as the official ones under test).

**4. Downloads: paging integrity and reconciliation, recorded separately.**
- **Paging integrity** (hard):
  - **Windows:** each request is widened by one minute on both sides, because the API's `start` and `end` are both inclusive. Records are then assigned locally to half-open intervals.
  - **Paging:** `sort=asc`, `limit=10000`, and every `next_page_token` is followed until null. A short page never ends paging.
  - **Failures:** a non-success response, a timeout or a malformed page is retried up to 3 times. A permission error is final, with no fallback. A page token seen twice fails.
  - **Page validation:** every page must carry `next_page_token`, the records key (`trades` or `bars`; an explicit null means no records on that page) and `symbol` equal to the requested symbol, and every record must be an object. A page missing any of these is malformed (retried, then incomplete), never treated as empty.
  - **Duplicates** are keyed by **(trading date, exchange, trade ID)**, the identity Alpaca staff give for historical trades. An exact duplicate is dropped and counted. The same key with different content fails.
  - **Records:** page counts, record counts, bytes and SHA-256 checksums.
  - **Any failure makes that date's coverage incomplete.** Every difference in that session is then **unexplained (coverage missing)**.
- **Reconciliation** (recorded, never conflated with paging): every minute of the date is rebuilt from the trades with the ALPACA profile and compared **exactly** with Alpaca's minute bar (open, high, low, close, volume, count). Each difference is recorded with its kind: "values differ", "vendor bar missing" or "vendor bar without trades". These are **aggregation or data differences, not proven missing pages**.
  - **A session with any unresolved reconciliation difference** has every difference unexplained ("unresolved reconciliation difference").
  - A reconciliation difference may be resolved only by a reviewed, written explanation, never by changing the rules after seeing the data.
- **Limitation, stated plainly:** paging integrity plus exact reconciliation is the strongest available evidence. Matching summary bars still don't prove that every individual trade was delivered; e.g. a trade dropped from both the trade feed and the bar input would go unseen. The results state this.

## If verification blocks
A field that ends `OTHER` or `UNDETERMINED`, outside the `F == 1` case, is **blocked**:
1. **Investigate first.** Look for more anchors, other yfinance call options, or the hourly/daily relationship. A failed initial expectation isn't, by itself, a reason to change the architecture.
2. While a field is blocked, **every task that writes it is blocked**:
   - a blocked `DIVIDEND_AMOUNT` blocks this task's dividend import;
   - a blocked D1 or H1 field blocks the matching part of M1-13 and of the M1-17 import command;
   - and in every case, **M1 completion** is blocked.
3. **Only if** investigation shows this source can't meet the raw-value requirement, a **proposed ADR** is written (e.g. an alternative data source, or an explicit adjusted-basis contract). It isn't adopted without review and acceptance. **A proposal alone doesn't unblock anything.** The blocked work resumes only after an accepted ADR, the matching updates to the architecture and specs, and their implementation.

- `IDENTITY_IF_NO_LATER_SPLIT` records with `F > 1` are rejected by the importer.

**Import:**
- importing the fixture gives the cited splits and the declared dividend amounts;
- a second import adds nothing;
- one changed dividend gives an `OBSERVED` revision 2, available from its observation time.

**Live check (`integration`, not run by default):**
- the full-history split call returns splits outside any requested window;
- the live columns match the fixtures.
