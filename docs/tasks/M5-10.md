## Contracts

The [M5 shared contracts](M5-README.md#shared-contracts) and accepted ADR-010 govern this task. Proposed rules for this task:

1. Core uses a distinct accounting-ledger consumer, with opt-in Consumer serialization taking consumer|name inside each event transaction before checking the processed mark. Existing consumer defaults remain unchanged. Then take account-control -> ledger locks; the dispatcher cannot be entered while already holding an account lock. Do not wrap a whole run in an outer transaction. Selected fills remain independently source-deduplicated; commit effects/processed mark together and replay original IDs after a crash.
2. Synchronization and readiness occur before new activated-account proposals or gate reads. Direct OrderStore create/state/fill mutation paths acquire the account-control lock before economic/reservation reads and reread under it; M4 direct fills did not hold it. Preserve fixed account-control -> ledger lock ordering and review the consumer/outbox lock graph for deadlocks. Never combine book and reservation reads across inconsistent cutoffs.
3. Worker consumes RESEARCH setup and captures evidence even with zero orders. At a fixed ReplayClock cutoff, alternate worker capture -> Core sync/compare -> worker gate; identical captures/unchanged sources reuse IDs and create no events. Defer NEW while merely waiting for the Core readiness token, without prematurely gate-rejecting it. Actual submissions still run the real gate, including expiry; cancels/recovery continue. The harness drains a finite pinned prefix with a work budget and reports INCOMPLETE on no progress/exhaustion. Snapshot calls stay bounded/outside transactions; R5 lost-connection propagation remains intact.
4. Wire only activated accounts to LEDGER and typed unavailability per D39. Before activation, retain historical M4 behavior/labels; after activation, no silent provisional fallback.
5. Preserve kill-switch Admin-only authority, deadline/stalled-call guards, UNKNOWN no-resend, account-scoped work and always-allowed cancels. Core never calls snapshot() or touches sim_broker schema.
6. No dependency is imported before this committed task. Use injected optional services/defaults so earlier records and legacy call sites remain compatible.

## Acceptance tests

- Two real role instances: zero-order setup -> worker seed/snapshot -> initial MATCH -> first proposal; then worker fill -> outbox -> Core journal -> worker snapshot -> reconciliation; same results through offline harness.
- Core crash before/after ledger commit and before processed mark: one posting only, no partial record.
- Worker snapshot timeout, ordinary exception and connection loss preserve bounded/stalled/reconnect behavior; no new order resubmission.
- A pending accounting gap blocks new proposal/submission; halted/unreconciled account still cancels.
- Concurrent fill and proposal cannot size from stale cash; one account replay/incident does not alter another.
- Two accounting consumer instances racing the same event produce one effect/processed mark and zero spurious unique-violation failures; a failed event still rolls back only itself.
- Zero-order and post-fill readiness converge at one fixed replay time; a deferred NEW stays NEW until a valid token, then passes the actual gate exactly once, while expiry and mismatches still block.
